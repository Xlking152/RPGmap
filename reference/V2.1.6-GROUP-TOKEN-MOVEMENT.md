# RPGmap v2.1.6 — Group Token Movement

## Goal

v2.1.6 extends the existing World V2 / Scene Token movement stack so an existing multi-selection can move as one rigid formation without introducing a persistent group document.

The intended interaction is:

1. Box-select or otherwise select multiple map Tokens.
2. Drag any Token already inside that selection.
3. The dragged Token becomes the leader while the other selected Tokens keep their relative `dx/dy` offsets.
4. Draw only the leader route to keep the map readable.
5. Translate the same route for every member and validate every segment with that member's own navigation context.
6. If any member is blocked, reject the whole formation.
7. If every member remains valid, commit all final Scene Token coordinates in one authoritative World commit.
8. Animate every Token along its translated route in the Renderer without intermediate World writes.

A group exists only while the movement plan exists. There is no `TokenGroup`, Formation, membership table, Scene group record, or World migration.

## Selection / leader semantics

Movement V3 preserves the current multi-selection only when the Token being dragged already belongs to it. The dragged Token becomes the primary selection and movement leader.

For each member, the controller records only transient offsets:

```js
{
  tokenId,
  dx: token.x - leader.x,
  dy: token.y - leader.y
}
```

Dragging a Token outside the current selection falls back to the existing single-Token behavior.

Changing selection while a movement plan is active cancels the plan so stale membership cannot be committed.

## Rigid route translation

If the leader starts at `L0` and has route points `L0, L1, ... Ln`, a member starting at `M0` receives:

```text
M0
M0 + (L1 - L0)
...
M0 + (Ln - L0)
```

This preserves the formation exactly. Members do not run independent pathfinding or choose different detours.

Each translated segment is nevertheless checked independently because Tokens can differ in:

- diameter
- elevation
- resolved Status collision bypass groups
- movement capability

A valid leader segment is therefore not sufficient by itself.

## Collision semantics

`MovementControllerV3.findGroupSegment()` asks the existing route inspector to validate the translated segment for every selected Token.

The route is invalid as soon as one member fails. The leader route is the only polyline drawn, but the failure identifies the blocked member and the whole endpoint preview becomes blocked/red.

There is no partial success such as “move the Tokens that can fit and leave the others behind”. That would silently destroy the formation and make authoritative rollback ambiguous.

Selected members are treated as one rigid context; v2.1.6 does not create a second collision authority or Formation navigation engine.

## Atomic World authority

`src/movement/token-runtime.js` adds transient planning APIs:

```js
planTokenGroupMove(tokenIds, leaderId, leaderPoints)
commitTokenGroupMove()
```

Before execution, the runtime re-reads every canonical Scene Token and verifies that:

- it is still on the map;
- its origin has not changed since planning;
- movement is still permitted by resolved Status capability;
- every translated segment is still navigable.

Only after all members pass does the runtime create one World draft containing every final Token coordinate and call:

```js
api.world.commit(world, {
  source: 'movement:group',
  reason: 'token.group-move',
  render: true,
})
```

Thus a formation is all-or-nothing at the canonical state boundary. v2.1.6 does not issue N sequential `token.move` World commits.

Existing Token-bound attack area anchors are updated inside the same World draft for each moved Token.

World operation schema remains `1`; the ordinary World diff/reducer layer can represent the changed Scene Tokens as one atomic operation batch without introducing a new persistent schema type.

## Render-only waypoint animation

Atomic canonical movement stores only final coordinates, but the visual route should still show the planned waypoints.

The Token Renderer therefore exposes a render-only preparation hook:

```js
api.renderer.prepareTokenVisualRoute(tokenId, points)
```

Immediately before the one canonical group commit, the movement runtime primes each Token with its translated waypoint queue. When the committed final state reaches the Renderer, the existing v2.1.4 `requestAnimationFrame` interpolation consumes that queue.

This preserves both properties:

- canonical state changes exactly once for the formation;
- users still see every Token traverse the planned route rather than teleport directly to the final coordinate.

Prepared routes never enter World, Scene, Actor, Combat, or Ruleset state. A failed canonical commit clears them.

`prefers-reduced-motion` continues to disable interpolation while preserving canonical group movement and endpoint previews.

## Group endpoint ghosts

The v2.1.4 movement Ghost renderer now reads the transient group preview members from Movement V3.

At the leader endpoint it renders one non-interactive Token ghost per member at:

```text
leader endpoint + member dx/dy
```

The leader still owns the visible route line. Showing all endpoint ghosts makes the final formation obvious without covering the map with parallel route polylines.

If any member is blocked, the whole preview uses the blocked visual state.

These ghosts remain render-only and are never selectable, targetable, collidable, or persisted.

## Elevation

Group movement modifies only map `x/y` placement. Each Token keeps its own `elevationFt`.

Because navigation is evaluated separately for each member, a flying/high-elevation Token can pass an obstacle that blocks a lower member, but the formation as a whole is still rejected when any required member cannot pass.

## Multiplayer / Combat permissions

Outside active Combat, ordinary Player group movement is permitted only when every changed Token resolves to an Actor the Player owns. Existing server authority validates every changed Token/Actor in the batch.

During active Combat, ordinary Players are explicitly limited to one moved Scene Token per World push. This remains true even when multiple Tokens are linked to the same current-turn Actor, preventing group movement from becoming a Combat Turn Lock bypass.

GM authority remains unrestricted by this Player-only rule and may group-move multiple Tokens during Combat for encounter administration.

Both client preflight and Local/LAN server access control enforce the same single-Token Player Combat boundary.

## Bundle budget baseline

v2.1.5 ended with only 201 bytes of headroom against a historical fixed total-JS ceiling. v2.1.6 formally rolls the bundle budget baseline to the released v2.1.5 commit:

```text
d31840247fba4d850f6f47054588686d747c60dd
```

The previous `initialJs * 0.90` rule was a one-time v2.1.0 chunk-splitting target. Since that reduction is already achieved, the new policy keeps initial JS from regressing above the v2.1.5 released payload while allowing at most 5% growth in total JS and CSS relative to that formal release baseline.

This is a baseline rollover, not an arbitrary threshold increase to make v2.1.6 pass.

## Compatibility / unchanged boundaries

v2.1.6 does not change:

- World schema: `2`
- operation schema: `1`
- Combat preference schema: `2`
- Infinite Horror Ruleset: `1.0.0`
- Lanzhou MapPackage data version: `1.0.5`
- Scene Token canonical authority
- Actor Ownership semantics
- v2.1.4 render-only Token interpolation
- v2.1.5 Combat Turn Origin Ghost semantics
- Feature State authority
- retired Character Runtime boundary

No persistent group entity or save migration is introduced.
