# RPGmap v2.1.5 — Combat Turn Origin Ghost

## Goal

v2.1.5 adds an FVTT-style combat turn origin marker without restoring Character Runtime or creating a second Scene Token.

For the active combatant:

1. When combat starts, capture the current canonical Scene Token position as the turn origin.
2. When `nextTurn()` selects a new combatant, replace the origin with that Token's current position.
3. Do not render an origin ghost while the live Token still overlaps the origin.
4. After the canonical Token leaves the origin, show a non-interactive translucent ghost at the stored origin for the rest of the turn.
5. On the next turn, replace the old origin. On combat end, the Combat State is cleared, so the ghost disappears.

## Authority model

The origin belongs to shared Combat State, not to a browser-local renderer cache.

`preferences.combatSystem` now normalizes to Combat schema `2` and can contain:

```json
{
  "schemaVersion": 2,
  "combat": {
    "state": "active",
    "round": 1,
    "turnIndex": 0,
    "turnOrigin": {
      "x": 120,
      "y": 80,
      "elevationFt": 15
    }
  }
}
```

`turnOrigin` intentionally stores only geometry. Turn identity already lives authoritatively in `combat.round` plus `combat.turnIndex`, and the active Token identity already lives in `combat.combatants[turnIndex]`. Duplicating `round`, `tokenId`, or `combatantId` inside the origin would create parallel sources of truth.

This lets GM and Players reconstruct the same origin after a page refresh or LAN reconnect while keeping the stored state minimal.

Combat schema `1` saves remain valid. `normalizeCombatState()` upgrades them in memory to schema `2` with `turnOrigin: null`; no World migration or manual save conversion is required.

## Capture points

The Combat Controller captures the current Token origin after:

- `startCombat()`
- every `nextTurn()`
- removal/deletion of the active combatant when that implicitly changes the current combatant

The capture reads the canonical Scene Token's `x`, `y`, and `elevationFt` and stores them through the existing CombatStore / World commit path.

`startCombat()` and `nextTurn()` clear the old origin before the Controller captures the new one. Removal of the active combatant also invalidates the old origin before a replacement is captured. This prevents a stale origin from being associated with a new turn.

## Renderer boundary

`src/combat/turn-origin-renderer.js` is an independent visual adapter.

It:

- reads shared `preferences.combatSystem`
- resolves the current combatant from `turnIndex`
- resolves that combatant's canonical Scene Token and Actor presentation
- compares the Token's current canonical `x/y` with the stored origin
- renders only when the Token has actually left the origin
- listens to state import/commit and map zoom changes
- rebuilds correctly after reconnect or refresh

It does not:

- create or mutate a Scene Token
- call `api.world.commit()` or `api.commitState()`
- participate in Selection
- participate in collision/navigation
- participate in AoE, damage, healing, or targeting
- expose a draggable or clickable map object

## Visual language

The combat origin is intentionally different from the v2.1.4 movement endpoint preview.

### Movement endpoint preview

Meaning: where the Token is planning to go.

- stronger preview treatment
- animated/dashed endpoint cue
- `预览` / `受阻`

### Combat turn origin

Meaning: where the current combatant began this turn.

- reuses the canonical Token visual model/portrait
- approximately one-third marker opacity
- permanent `起点 · X ft` tooltip
- no HP bar
- no Status badges
- pointer-events disabled

The origin pane is below the canonical Token pane. The renderer also hides the ghost while current coordinates equal the origin, avoiding a doubled Token appearance before movement or after returning exactly to the turn start.

## Interaction with v2.1.4 smooth movement

v2.1.4 keeps canonical movement server-authoritative while interpolating committed positions only in the Token Renderer.

v2.1.5 does not change that model.

When a committed Token position changes:

1. canonical World / Scene Token receives the authoritative destination;
2. the Token Renderer begins render-only interpolation from the previous visible position;
3. the same state commit causes the Combat Origin Renderer to see that canonical coordinates have left `turnOrigin` and reveal the start ghost;
4. the live Token moves smoothly away from that ghost;
5. no intermediate coordinate is written to World.

This produces the desired FVTT-like visual result while keeping server authority intact.

## Bundle discipline

The origin renderer deliberately reuses the existing Token presentation and CSS rather than carrying a second complete ghost styling implementation. The shared origin also stores only `x/y/elevationFt`, and the renderer performs its tiny coordinate comparison locally. This keeps the feature inside the existing production bundle budget without weakening the budget.

## Compatibility / unchanged boundaries

v2.1.5 does not change:

- World schema: `2`
- operation schema: `1`
- Infinite Horror Ruleset: `1.0.0`
- Lanzhou MapPackage data version: `1.0.5`
- Scene Token authority
- Actor ownership / Combat Turn Lock
- Feature State authority
- v2.1.4 render-only movement interpolation
- retired Character Runtime boundary

Only the Combat subsystem's internal preference schema advances from `1` to `2`, with backward normalization.
