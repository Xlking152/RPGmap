# RPGmap 开发说明

本文只保留当前仍有效的开发约定，避免与 README、操作指南和变更日志重复。

当前应用版本：**2.3.4**

## 1. 技术栈

- JavaScript / ES Modules
- Vite 8
- Leaflet 1.9.4
- polygon-clipping 0.15.7
- Lucide 1.30.0
- Node.js `^20.19.0 || >=22.12.0`
- Node 内置 `node:test`

内置地图通过 `src/map-package/builtins.js` 注册到 MapPackage Registry，并在 Active Scene 真正请求对应 package 时再动态载入 `default-map.js`。`main.js` 不直接构造兰州地图。新增地图应增加独立 MapPackage / Registry loader，而不是复制整套应用逻辑。

`src/main.js` 只负责 World Manager bootstrap。轻量 `src/ruleset/builtins.js` 提供 Ruleset 元数据和严格引用解析；完整 Ruleset、Leaflet、地图 CSS、地图引擎与非首屏系统必须在 World、Ruleset 与 Active Scene 的 MapPackage 引用确定后才动态加载。

## 3. 系统边界

### Core / Ruleset / MapPackage / World / Scene

核心原则：**Actor 属于 World；Token 属于 Scene；Core 提供能力；Ruleset 解释规则；MapPackage 提供地图内容。**

- Core 不应直接理解“B/L/A”“冻结点数”等特定规则词汇。
- Ruleset 的角色私有数据只放在 `Actor.system` 中，由 Actor Contract 规范化、解析和操作。
- World 绑定 Ruleset；Scene 绑定 MapPackage。不要按地图重新选择 Ruleset。
- 现代本地存档使用 `rpgmap:world:<worldId>:v1`；`rpg-map:<mapId>:v1` 只允许作为 legacy migration 输入。
- Runtime 创建前必须先解析 World → `World.ruleset` → Active Scene → `Scene.mapPackage`，再由 MapPackage Registry 加载地图。
- 同 MapPackage Scene 可在当前 Runtime 激活；跨 MapPackage Scene 必须先提交 canonical `activeSceneId`，再 reload Runtime，不在已初始化 Leaflet 上热替换整张 MapPackage。

#### World-first 启动

现代本地 World 使用 `rpgmap:world-catalog:v1` 保存轻量目录，使用 `rpgmap:world:<worldId>:v1` 保存完整状态。启动顺序固定为：

```text
检测 Local/LAN Server
  → 读取、选择或创建 World
  → 严格解析 world.ruleset
  → 定位 world.activeSceneId
  → 读取 scene.mapPackage
  → 动态加载 Map Runtime 与 MapPackage
  → 规范化 Actor / Token / Status / Health
  → 注册 UI 与多人系统
```

未知、缺失或版本不兼容的 Ruleset/MapPackage 必须明确失败。默认 `infinite-horror` 只允许用于新 World 或明确的旧 SaveV2 迁移，不能覆盖已有 World 的引用。空 LAN Server 与浏览器离线模式使用同一解析顺序。

#### 持久化与写入权威

- World schema 3 是 Actor、Scene、Token、Marker、Fog、StatusDefinition、Combat 与 Scene 运行状态的持久化唯一权威；兼容存储键仍沿用 `worldV2`。
- `Actor.system` 的结构、派生、展示和操作由 Ruleset Contract 解释。
- Linked Token 才能修改 Base Actor；Unlinked Token 只写自身 `actorDelta`。
- NPC/召唤物 Token 必须 Unlinked；其 Health、伤势、状态、资源和当前形态操作缺少 `tokenId` 时必须返回 `instance_target_required`。
- `preferences.entitySystem`、`preferences.featureStates` 和其他兼容投影只读生成，不得反向覆盖 World。
- 普通交互使用 operation schema 3 的 `document.batch`。写入必须包含 Document type/id/parent、注册过的安全 intent、data 与可选 precondition；客户端不得提交任意 JSON path。`api.world.performOperations()` 只作为旧调用点的兼容包装器，新 UI 和 Movement 使用 `api.documents.dispatch()` / `dispatchBatch()`。
- 服务端提交后按会话广播 `document.batch.committed`，其中 `changes` 只包含 create/update/delete/move/append 的目标 Document 与 changed fields。完整 snapshot 只允许初始化、显式导入/恢复、无法续传的 revision 缺口、Audience 身份变化和跨 MapPackage Scene。
- operation envelope 使用 `operationId`、`expectedRevision`/`baseRevision` 和有界 batch。离线 reducer 与 LAN Server 复用同一 operation 语义，服务器必须重新校验权限、引用与载荷。
- unknown operation/path、revision 冲突、重复 operationId、权限失败与损坏载荷必须返回稳定错误，不能静默改写或回退。
- `document.batch.committed` 固定包含 `baseRevision`、`revision`、Audience-safe `patch`、`changeSet`、`changes`、`results`，移动还可包含经过精确可见性裁剪的 `motion`。客户端 Collection 只更新目标 Document 并发出 `document:create/update/delete/move`；普通 patch 不得重新进入 import/migrate 或整场景重建。
- LAN Server 必须先写盘，再为每个 Session 从缓存投影生成定向 patch；不可见操作也要发送无内容 revision 前进消息。权限或视野来源变化使用独立 `audienceRevision` 和完整 Audience snapshot，不得把玩家投影写回 canonical World。

`changeSet` 是渲染失效提示，不是第二份权威数据。它覆盖 Actor、各 Scene Token、Scene、Feature State、Fog dirty bounds、Combat、Chat 和 StatusDefinition；所有 ID 必须已按接收者 Audience 裁剪。客户端应用 patch 后仍要校验 World 引用和 revision 连续性。

#### Local/LAN WAL 与续传

- `map/world.json` 是压缩后的基线快照，`map/world.operations.ndjson` 是 ACK 前持久化的写前日志。每行必须包含连续 revision、operationId、canonical patch、时间和 checksum；最后一行不完整可截断，中间损坏必须停止加载。
- 每 100 revision、60 秒或 WAL 达到 8 MB 时写入新的原子 `world.json` 并轮换 WAL。导入、迁移和恢复仍先做完整备份。
- 服务端保留最近 256 次或至少 5 分钟 commit。hello 的 `resumeRevision` 与 Audience 指纹匹配时补发逐会话安全差量；身份、Access revision 或视野源变化必须拒绝旧续传并发送新投影。
- 移动使用 `Token/move/token.movePath`，一次请求携带全部 tokenIds、waypoints 与 expectedOrigins。服务端逐 Token、逐段验证；只有移动前后均精确可见的接收者可得到完整 motion。

#### Scene Feature State

每个 Scene 拥有独立的 `featureStates: Record<featureId, object>`。破坏/恢复历史继续保存在 `sceneEvents`，不得把 damage 派生结果复制到 Feature State。

`scene.featureState.patch` 使用递归 JSON Merge Patch：字段值 `null` 删除字段，根 `null` 删除整条记录，未知安全字段保留。当前写入仅 GM 可用，Feature State 与 Status 副作用可以放在同一 operation batch 中。旧 `preferences.featureStates` / `featureInteractions` 只在完整存档迁移入口读取；发生真实冲突时返回 `feature_state_migration_conflict` 并保留原始存档。

### EntitySystem

`Actor` 负责“这个角色是谁”。Core 使用通用文档外壳：

```js
Actor {
  id,
  name,
  img,
  type,        // pc | npc | summon | other
  partyId,
  prototypeToken: {
    texture: { src },
    color,
    diameterMeters,
    showName
  },
  publicProfile: {
    schemaVersion: 1,
    summary,
    appearance,
    knownFacts,
    visibleStatusDefinitionIds
  },
  system,      // Ruleset 私有数据
  effects,
  ...
}
```

`Token` 负责“这个角色在当前场景中是什么状态”：

- actorId
- map location
- selection
- hidden / locked
- rotation / size / elevation
- actorLink / actorDelta
- controllerUserIds / visibility / vision
- texture / color 等实例级外观覆盖

Linked Token (`actorLink: true`) 直接使用 World Actor，只允许 PC 等共享角色场景。Unlinked Token (`actorLink: false`) 使用 Base Actor + `actorDelta` 形成 Synthetic Actor；NPC 与召唤物创建时由客户端和服务器共同强制 Unlinked。实例生命、状态、资源和当前形态变化只写回该 Token 的 `actorDelta`，不能污染模板 Actor 或同模板的其他 Token。

Ruleset `actor.instances` 负责创建、规范化、从运行 Actor 生成 Delta，以及模板更新后的实例重整。Infinite Horror Delta 必须显式保存 `system.currentFormId`、`system.runtime` 和 `effects`；Forms、属性、技能、头像及生命上限仍从模板动态继承。模板降低生命上限时，只能截断超限的当前生命；删除仍被实例使用的形态返回 `variant_in_use`。

Actor/Token 外观覆盖顺序固定为：

```text
Token 显式实例覆盖
  > Ruleset 当前 Form presentation
  > Actor.prototypeToken / Actor.img 默认值
```

Token 的显式图片、颜色或其他实例覆盖只影响该 Scene Token，不反向修改 Actor 或同源 Token。

#### Actor Sheet V3 与权限上下文

正式角色卡由 `src/entities/sheet/actor-sheet.js` 组合 Header/Summary、Public Profile、Resources/Health、Checks/Combat、Status 与 Token Parts。`ui-live.js` 负责窗口生命周期、事件协调和发起权威 operation；Play/Edit、LIMITED 与 OBSERVER 的 DOM 结构必须在渲染前由 Sheet Context 决定，禁止用 MutationObserver 事后禁用字段。

```js
api.permissions.actorLevel(actorId)
api.permissions.can(action, context)
createSheetContext({ permissionLevel, mode, actor, token, sceneId })
```

权限等级来自 Local/LAN Access 数据，不从 Actor 文档读取 `ownership`。OWNER/GM 的 Play 模式可执行运行时操作，Edit 模式才修改结构字段；OBSERVER 完整只读；LIMITED 只能渲染 AudienceProjection 已裁剪的公共卡。Actor OWNER 不自动获得 monster/npc/summon Token 控制权。

`Actor.publicProfile` 是 Core 可识别的向后兼容公开外壳，不属于 `Actor.system`。旧 Actor 标准化为空档案；禁止自动复制 Ruleset 的背景、简介或外观。更新只允许 GM 通过 `actor.publicProfile.update`，服务端负责长度、数组数量、状态定义引用和去重校验。

Actor 权限写入统一使用 `api.multiplayer.updateActorOwnership({ actorId, changes })`。请求携带 Access `baseRevision`，全部变化一次原子提交；revision 过期或任一非法输入会拒绝整批并刷新权限目录。Token 可见性、控制者和视野授权继续使用独立入口。

### AudienceProjection / Vision / Fog

`projectStateForAudience()` 是服务端与测试共用的纯函数。GM 获得完整权威状态；Player 只获得其身份、队伍、当前实时视野和明确授权允许的数据。Actor 权限按 NONE/LIMITED/OBSERVER/OWNER 区分，Token 可见性、Actor 查看/编辑、实例控制与视野授权不得互相替代。可见但未授权的 NPC 使用 schema 合法的 LIMITED Actor/Token，只保留最小 prototypeToken、公开名称/头像/类型、标准化 `publicProfile`、空 `system`/`effects` 和限制标记。精确可见 Token 可附带仅含名称、图标、颜色、分类和层数的 `publicStatuses`；它必须从当前 Token 的最终 Linked/Synthetic Actor 状态计算并受 `visibleStatusDefinitionIds` 白名单约束。严禁包含状态/定义 ID、备注、持续时间、来源、capabilities、changes、Delta、生命、控制者或其他同 Actor Token 的独立状态。GM-only 与敌方实时视野裁剪必须同时作用于快照、operation patch、Combat、Chat、Status/Effect、Access Actor 目录和查询结果。

当前视野来源属于 Session，不写入 World。LAN 使用 `vision.source.set/ack`，服务器根据权威 Token、Synthetic Actor、Ruleset `vision.describe()`、Effect 和 Token override 计算圆形范围；Player 不能提交坐标或探索格。来源移动时，服务端把移动前后位置的扫掠圆合并到 `Scene.fog.exploredByParty[partyId]` 的 5 米行区间网格。

同队只共享已探索历史，不共享其他会话的实时视野。`scene.fog.reset` 与 `scene.fog.hide` 仅 GM 可用；重新隐藏扣除网格，角色再次进入后仍可重新探索。首期不做墙体、门、高度或精确 LOS。Fog Canvas 只遮挡地图显示，不改变 Token 尺寸、碰撞、选择或导航，也不承诺隐藏已下载的 MapPackage 底图资产。

Token `visibility.mode` 为 `public / party / gm / users`；`gm` 始终优先。模糊敌影的标识由 Session 随机密钥生成，不包含真实 Token ID，并且只保留 5 米量化坐标和体型。Infinite Horror 的 `status-invisible` 通过通用 `capabilities.visibility = "invisible"` 表达，Ruleset 以外的投影代码只读取 capability，不写死状态 ID。

### SelectionSystem

SelectionSystem 统一负责当前 Token 选择集合。Combat、角色测距、Damage、Healing 等系统应读取 SelectionSystem，而不是各自维护另一套选择状态。

### MovementSystem

MovementSystem 只处理 Token 的地图移动行为：

- 普通拖放直线规划
- `Ctrl`/`Cmd` 分段 waypoint，`F` 添加、`Alt+F`/右键撤销、`Enter` 确认、`Esc` 取消
- 有界 1m 直线碰撞检测与手动拐点
- snap
- route distance
- Ghost preview
- 50ms/最多 8 步的有界 WASD 合并

预览、鼠标提交、WASD 与群组最终提交必须共用同一结构化校验，失败结果包含稳定 code/reason。复杂速度、行动点和规则系统暂不写死在 MovementSystem 中。

### Infinite Horror Detection

Ruleset 拥有侦测数据的规范化、导入、派生和呈现。基础 Form 保存精确/模糊范围及感官能力，Unlinked Token 的运行时覆盖保存在 `actorDelta`。Core 只消费 Ruleset `vision.describe()` 结果，不读取 Infinite Horror 私有路径。环境亮度仅实现明亮/昏暗/黑暗的范围降级；本版不实现墙体 LOS。

XLSX 导入必须按工作表名和标签匹配，保留原始值及结构化警告。可用 `npm run test:xlsx -- --file <path>` 对真实工作簿运行生产导入链；测试命令只读取文件，不应把用户工作簿复制进仓库或发布包。

### MeasurementSystem

MeasurementSystem 负责纯几何 Ruler；MovementSystem 负责实际移动路线与移动成本。二者共用高层路径标签，但不混用距离计算逻辑。

### Health / Damage / Healing

Health 是独立规则域，**HP 不再属于 Generic Resource**。

Infinite Horror 的基础生命上限：

```js
form.healthBase = {
  baseMax: 20
}
```

普通生命运行时：

```js
system.runtime.health = {
  mode: 'simple',
  maxOverride: null,
  current: 20,
  wounds: { bashing: 0, lethal: 0, aggravated: 0 }
}
```

B/L/A 伤势运行时：

```js
system.runtime.health = {
  mode: 'wound-track',
  maxOverride: null,
  wounds: {
    bashing: 0,
    lethal: 0,
    aggravated: 0
  }
}
```

`system.runtime.resources` 只保存真正的通用资源，例如精力、意志和自定义能量，不得重新加入 `hp`。

Core Health 只负责：Actor / Synthetic Actor 目标解析、权限与去重、`actorDelta` 写回、持久化/事件/联机桥接，以及 Health UI host。Infinite Horror Ruleset Health 负责：生命上限、Simple HP、B/L/A、伤害/恢复、模式转换、死亡/昏迷/伤势状态和 Health presentation。

新代码通过 Actor Contract 操作 Health：

```js
performActorOperation(actor, {
  type: 'health.damage',
  amount: 3,
  damageType: 'L'
});

performActorOperation(actor, {
  type: 'health.runtime',
  operation: { type: 'set-current', value: 12 }
});

const health = deriveActorDocument(actor).health;
```

禁止通过以下旧结构修改生命：

```js
form.resourceBases.hp
system.runtime.resources.hp
resource.set-current({ resourceId: 'hp' })
resource.set-max({ resourceId: 'hp' })
```

新 Effect / Status 对生命上限的修改使用 `system.health.max`。旧存档里的 `resources.hp.max` 只允许在 Ruleset legacy 读取/迁移边界中识别，不得由新 UI、新定义或新业务代码生成。

DamageSystem 与 HealingSystem 只负责将“最终伤害”或“已经按规则换算后的实际恢复量”应用到所选 Token，不应把所有游戏规则写死在 UI 中。

### StatusSystem

StatusSystem 使用 schema 4：`statusDefinitions[]` 保存 buff/debuff/neutral 定义、白名单 changes/capabilities 和可选默认持续时间；`actor.effects[]` 保存 Linked Actor 状态，Unlinked Token 的实例状态只保存在 `actorDelta.effects`。`StatusInstance.duration` 使用 turns/rounds 的 initial/remaining，停用时暂停；服务器权威 `combat.advance` 原子推进回合与持续时间，到期状态写为 disabled 并记录 `expiredAt`。昏迷、死亡与规则派生状态只在解析时派生，不重复写入存档。

局域网状态写入只作为 `world.operation` 中的 `status.apply/remove/setStacks/setEnabled/update/batch/definition.*`，以 `operationId` 去重，并在服务器完成 schema 校验、备份和原子写盘后广播。定义导入必须整体校验、整体提交，冲突返回全部 ID；内置定义不可覆盖或删除。Feature 与状态组合操作使用一次权威 operation batch，不允许先写 Feature 再补发状态。

### ChatSystem / Game Log

聊天、战斗、伤害、恢复以及后续骰点 / 检定都应统一写入 ChatSystem / Game Log，不为每个子系统单独维护历史窗口。

### AppShell UI

UI 负责组织系统入口，不应复制 Entity / Movement / Combat / Health / Scene 的业务状态机。新增 UI 行为优先调用已有系统 API。

## 4. MapPackage 原则

地图内容与通用引擎分离。MapPackage 至少应提供：

```js
{
  id,
  title,
  version,
  width,
  height,
  metersPerUnit,
  initialView,
  features,
  createSvg()
}
```

可按地图需要增加：

- navigation
- roadBuffers
- destructibleCategories
- liquidBodies
- floodRules
- artAssets

地图坐标约定保持：左上角原点，X 向右，Y 向下。

MapPackage 必须通过 Registry 注册/发现。Built-in package 也遵循同一 Contract；未来 External MapPackage 安装/导入应复用 Registry，而不是另建平行 bootstrap。

## 5. Actor XLSX 导入

当前 `character-sheet-v1` 只允许读取：

- `角色概览`
- `具体数值表`

不得为了计算结果去读取：

- `购买清单`
- `特性与技能`
- `计算器`

导入器只使用工作簿中已经保存的最终缓存值，不实现 Excel 公式引擎。Excel 单元格地址必须封装在 Ruleset importer / template 内，不应泄露进 Core Actor model 或 UI。

导入 DTO 可以继续使用 `resources.hp` 表示 Excel 中读取到的生命字段，但进入 Actor System 后必须立即转换为 `form.healthBase`；导入 DTO 不是运行时数据模型。

## 6. 数据分层

```text
Imported / Base
      ↓
Current Form
      ↓
Runtime
      ↓
Effects
      ↓
Resolved Value
```

重新导入角色卡时，不应无条件覆盖当前 HP、精力、意志、自定义资源、不良状态当前值和临时效果。

Infinite Horror Actor System 当前 schema 为 **V3**。旧 HP 数据只允许出现在明确的 import / normalize / migration 边界：

- `form.resourceBases.hp` → 一次性迁移为 `form.healthBase.baseMax`。
- `system.runtime.resources.hp` → 仅作为旧数据迁移输入，规范化后删除。
- 已存在的 `runtime.health` 优先于陈旧 HP Resource 镜像，避免覆盖真实 B/L/A 伤势。
- 旧 Synthetic Actor HP delta 迁移到 `actorDelta.system.runtime.health`。
- 旧生命上限 Effect 路径只在 legacy 解析边界兼容；新内容使用 `system.health.max`。

World schema 2 → 3 迁移只允许在完整存档入口执行，并在首次写回前走现有备份机制。旧 Actor 默认迁移为 `pc / party-default`；旧 Token 保留 `actorLink`，`hidden: true` 转换为 `visibility.mode = "gm"` 并删除旧权威字段；每个 Scene 初始化空 Fog。迁移必须幂等并保留未知安全字段，规范化不能成为迁移替代品。

不要为了旧测试、旧 UI 或旧调用重新建立双写字段或薄转发模块。兼容逻辑应尽可能靠近数据入口，并由迁移回归测试保护。

## 7. 日常开发流程

本地开发：

```bash
npm ci
npm test
npm run dev
```

生产构建：

```bash
npm run build
```

修改功能时遵守：

1. 从 `main` 建立独立功能分支，不直接在 `main` 开发功能。
2. 优先修改对应子系统；`src/main.js` 保持轻量 bootstrap，地图业务进入明确的 Runtime/系统模块。
3. 为可独立验证的底层逻辑补充 `node:test`。
4. 不提交 `node_modules/`、`dist/`、测试缓存或本地运行垃圾。
5. 不提交用户真实角色卡作为测试 fixture；使用最小合成数据。
6. 功能开发期间使用 Draft PR 汇总改动；未完成测试前不合并 `main`。
7. 发布包必须从干净依赖环境重新构建，不使用临时验证 stub 或本地残留文件作为正式源码来源。

## 8. 版本约定

应用版本使用 `MAJOR.MINOR.PATCH`。

- Bug 修复建议 Patch，例如 `1.3.1`。
- 完整功能 / 子系统建议 Minor，例如 `1.4.0`。
- 不兼容存档、World 数据或服务器协议建议 Major，例如 `2.0.0`。

版本号变化不是开发者单方面自动决定。达到新的版本节点时：

1. 根据改动范围提出建议版本及理由。
2. **必须得到明确确认后**才能修改版本号。
3. 同步更新 `package.json`、相关页面 / 文档版本信息、`CHANGELOG.md` 与 `文档/操作指南.md`。
4. GitHub Release 使用 `vX.Y.Z`，例如 `v1.3.0`。

普通提交、测试包、Draft PR 和 CI 构建编号都不会自动提高应用版本。

## 9. 固定测试与正式发布流程

RPGmap 后续默认采用以下流程：

```text
功能开发
   ↓
功能分支 + Draft PR
   ↓
代码级测试 / 语法检查 / 定向测试
   ↓
生成测试运行包
   ↓
实际操作测试
   ↓
问题反馈 → 继续在同一功能 PR 修复
   ↓
功能稳定
   ↓
提出语义版本号
   ↓
明确确认版本号
   ↓
更新版本信息 + 变更日志 + 操作指南
   ↓
PR 合并 main
   ↓
GitHub Actions 干净构建
   ↓
npm ci → npm test → npm run build
   ↓
组装正式运行包
   ↓
GitHub Tag / Release vX.Y.Z
```

### 测试包原则

- 测试包用于实际体验，不等同正式 Release。
- 测试包必须对应明确的 branch / commit，并在包名或 `VERSION.json` 中标识。
- 打包前检查关键源码完整性，禁止混入测试 stub。
- 不包含 `.git`、`node_modules`、tests、cache、构建日志等开发垃圾。
- 如果测试发现问题，优先在原功能分支 / PR 中继续修复，再重新生成测试包。

### 正式 Release 原则

正式 Release 应由 `.github/workflows/publish-local-server-release.yml` 从 `main` 干净构建，至少执行：

```text
npm ci
npm audit --registry=https://registry.npmjs.org --audit-level=high
npm test
npm run build
npm run check:bundle
npm run package:local-server
```

正式运行包应包含：

```text
RPGmap-vX.Y.Z/
├─ app/                    已编译 Web Client
├─ start-rpgmap.bat        Windows 启动入口
├─ launcher.mjs            单入口启动器
├─ server.mjs              本地 HTTP Server
├─ access-control.mjs      Local/LAN 身份与权限
├─ portable-storage.mjs    便携数据目录
├─ world-schema.mjs        Server World 校验
├─ world-v2.mjs            World V2 投影/校验
├─ world-operations.mjs    内联的通用 operation reducer
├─ ruleset-authority.mjs   内联的 Ruleset 实例/投影权威
├─ status-*.mjs            Status 权限与操作
├─ VERSION.json            版本、Tag、Commit、端口等信息
├─ map/uploads/            上传目录（初始为空）
├─ map/backups/            备份目录（初始为空）
└─ docs/OPERATION-GUIDE.md 唯一随包文档
```

同时生成：

```text
RPGmap-vX.Y.Z.zip
RPGmap-vX.Y.Z.zip.sha256
```

Release 要求：

- Tag 与应用版本一致，例如 `v1.3.0`。
- 正式版本默认发布为 GitHub Release，而不是 prerelease，除非明确决定发布测试版 / RC。
- Release ZIP 只带 `docs/OPERATION-GUIDE.md` 作为长期操作文档，不复制源码 `reference/`、过程文档或开发说明。
- Release ZIP 优先包含预编译 `app/`，使用户无需自行执行 `npm ci` / `npm run build`。
- `VERSION.json.commit` 必须是完整 40 位 Git commit，禁止正式包出现 `local-build`；`worldSchema`、`operationSchema`、`statusSchema` 和 `accessSchema` 必须分别与源码常量一致。
- 统一 verifier 必须检查精确目录集合、唯一 BAT、版本/commit、manifest、动态 Runtime、29 个兰州 WebP、ZIP SHA-256 与体积预算。
- Release Notes 以对应版本的 `CHANGELOG.md` 为主要来源，并说明 Source Commit。
- 同一应用版本不重复发布不同正式包；如果正式发布后需要修复，应按语义化版本规则进入新的 Patch / Minor 版本。

## 10. Server 演进原则

当前 `deployment/local-server/` 是本地 / 局域网的服务器权威运行时。后续服务器能力按 `文档/未来规划.md` 推进：

```text
Static Server
  ↓
World Store
  ↓
REST API
  ↓
WebSocket
  ↓
GM / Player Permissions
  ↓
Multiplayer VTT
```

最终由 Server 成为 authoritative state，Client 负责输入、显示和局部预测。
