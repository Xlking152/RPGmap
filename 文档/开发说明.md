# RPGmap 开发说明

本文只保留当前仍有效的开发约定，避免与 README、操作指南和变更日志重复。

当前应用版本：**1.6.3**

## 1. 技术栈

- JavaScript / ES Modules
- Vite 8
- Leaflet 1.9.4
- polygon-clipping 0.15.7
- Lucide 1.30.0
- Node.js `^20.19.0 || >=22.12.0`
- Node 内置 `node:test`

## 2. 目录职责

```text
src/
├─ app/           持久化与应用辅助
├─ chat/          ChatSystem / Game Log
├─ combat/        CombatSystem / 先攻与回合
├─ damage/        DamageSystem
├─ engine/        地图核心、几何、导航、场景状态与兼容层
├─ entities/      Actor / Token / Form / Runtime / Effects / XLSX
├─ healing/       HealingSystem
├─ health/        SimpleHP / WoundTrack / Token 生命条
├─ maps/          独立 MapPackage
├─ measurement/   Ruler / 角色测距
├─ movement/      Token MovementSystem
├─ path/          Movement / Ruler 共用路径标签
├─ render/        场景和地图表现
├─ selection/     Token 单选、多选与框选
├─ status/        Actor/Token 状态、派生状态、能力解析与状态 UI
└─ ui/            AppShell UI

tests/            自动化测试
deployment/       本地服务器与发布设施
文档/             操作指南、未来规划、开发说明
```

当前默认地图通过 `src/map-package/default-map.js` 载入兰州 Reference MapPackage；地图内容不是 RPGmap Core 本身。新增地图应优先增加独立 MapPackage，而不是复制整套应用逻辑。

## 3. 系统边界

### EntitySystem

`Actor` 负责“这个角色是谁”：

- identity / avatar
- Forms
- resources
- attributes
- checks
- Base / Runtime / Effects

`Token` 负责“这个角色在当前场景中是什么状态”：

- actorId
- map location
- selection
- hidden / locked
- rotation / size 等后续场景属性

### SelectionSystem

SelectionSystem 统一负责当前 Token 选择集合。Combat、角色测距、Damage、Healing 等系统应读取 SelectionSystem，而不是各自维护另一套选择状态。

### MovementSystem

MovementSystem 只处理 Token 的地图移动行为：

- drag planning
- waypoint
- 有界 1m 直线碰撞检测与手动拐点
- snap
- route distance
- Ghost preview

复杂速度、行动点和规则系统暂不写死在 MovementSystem 中。

### MeasurementSystem

MeasurementSystem 负责纯几何 Ruler；MovementSystem 负责实际移动路线与移动成本。二者共用高层路径标签，但不混用距离计算逻辑。

### Health / Damage / Healing

HealthSystem 负责角色生命模型，当前提供：

- `SimpleHP`：通用当前值 / 最大值。
- `WoundTrack`：完好 / B / L / A 生命槽。

DamageSystem 与 HealingSystem 只负责将“最终伤害”或“已经按规则换算后的实际恢复量”应用到所选 Token，不应把所有游戏规则写死在 UI 中。

### StatusSystem

StatusSystem 使用 Entity schema v3：`statusDefinitions[]` 保存自定义定义，`actor.effects[]` 保存跨形态状态，`token.effects[]` 保存单个地图实例状态。昏迷、死亡与不良状态阈值只在解析时派生，不重复写入存档。

局域网状态写入只走 `status.apply/remove/setStacks/batch/definition.*`，以 `operationId` 去重，并在服务器完成 schema 校验、备份和原子写盘后广播。Feature 与状态组合操作使用一次带 `operationId` 的权威 World 提交，不允许先写 Feature 再补发状态。

### ChatSystem / Game Log

聊天、战斗、伤害、恢复以及后续骰点 / 检定都应统一写入 ChatSystem / Game Log，不为每个子系统单独维护历史窗口。

### AppShell UI

UI 负责组织系统入口，不应复制 Entity / Movement / Combat / Health / Scene 的业务状态机。新增 UI 行为优先调用已有系统 API。

## 4. MapPackage 原则

地图内容与通用引擎分离。MapPackage 至少应提供：

```js
{
  id,
  title,
  version,
  width,
  height,
  metersPerUnit,
  initialView,
  features,
  createSvg()
}
```

可按地图需要增加：

- navigation
- roadBuffers
- destructibleCategories
- liquidBodies
- floodRules
- artAssets

地图坐标约定保持：左上角原点，X 向右，Y 向下。

## 5. Actor XLSX 导入

当前 `character-sheet-v1` 只允许读取：

- `角色概览`
- `具体数值表`

不得为了计算结果去读取：

- `购买清单`
- `特性与技能`
- `计算器`

导入器只使用工作簿中已经保存的最终缓存值，不实现 Excel 公式引擎。Excel 单元格地址必须封装在 importer / template 内，不应泄露进 Actor model 或 UI。

## 6. 数据分层

角色基础值与跑团运行状态必须分开：

```text
Imported / Base
      ↓
Current Form
      ↓
Runtime
      ↓
Effects
      ↓
Resolved Value
```

重新导入角色卡时，不应无条件覆盖当前 HP、精力、意志、自定义资源、不良状态当前值和临时效果。

## 7. 日常开发流程

本地开发：

```bash
npm ci
npm test
npm run dev
```

生产构建：

```bash
npm run build
```

修改功能时遵守：

1. 从 `main` 建立独立功能分支，不直接在 `main` 开发功能。
2. 优先修改对应子系统，不继续扩大 `src/engine/app.js`。
3. 为可独立验证的底层逻辑补充 `node:test`。
4. 不提交 `node_modules/`、`dist/`、测试缓存或本地运行垃圾。
5. 不提交用户真实角色卡作为测试 fixture；使用最小合成数据。
6. 功能开发期间使用 Draft PR 汇总改动；未完成测试前不合并 `main`。
7. 发布包必须从干净依赖环境重新构建，不使用临时验证 stub 或本地残留文件作为正式源码来源。

## 8. 版本约定

应用版本使用 `MAJOR.MINOR.PATCH`。

- Bug 修复建议 Patch，例如 `1.3.1`。
- 完整功能 / 子系统建议 Minor，例如 `1.4.0`。
- 不兼容存档、World 数据或服务器协议建议 Major，例如 `2.0.0`。

版本号变化不是开发者单方面自动决定。达到新的版本节点时：

1. 根据改动范围提出建议版本及理由。
2. **必须得到明确确认后**才能修改版本号。
3. 同步更新 `package.json`、相关页面 / 文档版本信息、`CHANGELOG.md` 与 `文档/操作指南.md`。
4. GitHub Release 使用 `vX.Y.Z`，例如 `v1.3.0`。

普通提交、测试包、Draft PR 和 CI 构建编号都不会自动提高应用版本。

## 9. 固定测试与正式发布流程

RPGmap 后续默认采用以下流程：

```text
功能开发
   ↓
功能分支 + Draft PR
   ↓
代码级测试 / 语法检查 / 定向测试
   ↓
生成测试运行包
   ↓
实际操作测试
   ↓
问题反馈 → 继续在同一功能 PR 修复
   ↓
功能稳定
   ↓
提出语义版本号
   ↓
明确确认版本号
   ↓
更新版本信息 + 变更日志 + 操作指南
   ↓
PR 合并 main
   ↓
GitHub Actions 干净构建
   ↓
npm ci → npm test → npm run build
   ↓
组装正式运行包
   ↓
GitHub Tag / Release vX.Y.Z
```

### 测试包原则

- 测试包用于实际体验，不等同正式 Release。
- 测试包必须对应明确的 branch / commit，并在包名或 `VERSION.json` 中标识。
- 打包前检查关键源码完整性，禁止混入测试 stub。
- 不包含 `.git`、`node_modules`、tests、cache、构建日志等开发垃圾。
- 如果测试发现问题，优先在原功能分支 / PR 中继续修复，再重新生成测试包。

### 正式 Release 原则

正式 Release 应由 `.github/workflows/publish-local-server-release.yml` 从 `main` 干净构建，至少执行：

```text
npm ci
npm test
npm run build
```

正式运行包应包含：

```text
RPGmap-vX.Y.Z/
├─ app/                    已编译 Web Client
├─ server.mjs              本地 HTTP Server
├─ start-rpgmap.bat        Windows 启动入口
├─ README.md               启动摘要与文档入口
├─ VERSION.json            版本、Tag、Commit、端口等信息
├─ map/                    World / upload / backup 数据目录
└─ docs/                   需要随包附带的长期文档
```

同时生成：

```text
RPGmap-vX.Y.Z.zip
RPGmap-vX.Y.Z.zip.sha256
```

Release 要求：

- Tag 与应用版本一致，例如 `v1.3.0`。
- 正式版本默认发布为 GitHub Release，而不是 prerelease，除非明确决定发布测试版 / RC。
- Release ZIP 必须带 `README.md` 启动摘要和 `docs/OPERATION-GUIDE.md` 操作指南，至少覆盖启动、角色导入、Token 选择 / 框选、移动、测距、战斗、伤害、恢复、生命条和主要快捷键。
- Release ZIP 优先包含预编译 `app/`，使用户无需自行执行 `npm ci` / `npm run build`。
- Release Notes 以对应版本的 `CHANGELOG.md` 为主要来源，并说明 Source Commit。
- 同一应用版本不重复发布不同正式包；如果正式发布后需要修复，应按语义化版本规则进入新的 Patch / Minor 版本。

## 10. Server 演进原则

当前 `deployment/local-server/` 是本地 / 局域网的服务器权威运行时。后续服务器能力按 `文档/未来规划.md` 推进：

```text
Static Server
  ↓
World Store
  ↓
REST API
  ↓
WebSocket
  ↓
GM / Player Permissions
  ↓
Multiplayer VTT
```

最终由 Server 成为 authoritative state，Client 负责输入、显示和局部预测。
