# RPGmap 未来规划

当前开发基线：**V1.5.0 Candidate**。

目标：在已经完成的 MapPackage / Feature Capability / Feature State / Feature Operations 分层上，继续把 RPGmap 发展为类似 Foundry VTT 的自托管 Web 跑团平台。后续功能必须沿用“地图描述内容，Core 执行规则”的边界，不再把地图类别或单张地图逻辑写回通用系统。

## 一、V1.5 已完成基础

### MapPackage / Reference Map

- 兰州城已整理为 Reference MapPackage。
- Runtime 不读取 `reference/`，地图在 build 时打进客户端。
- Layer Plan、Feature ID、Capability、Navigation effect、taxonomy 已有统一契约。
- Minimal Reference Map 用于验证 Core 不依赖兰州类别。

### Feature Interaction

- 统一 Feature State：`open / intact|partial|destroyed / custom`。
- 统一 Feature Operations：`inspect / enter / exit / damage / restore / open / close`。
- Generic Feature UI 不再依赖 `building / gate` 等地图类别。
- Open / Close 已与 Navigation、SVG、Save、Multiplayer World State 接通。
- V1.5 新增通用 **Feature Control Layer**：openable Feature 可在地图上直接点击开关；destroyed 后控件隐藏；兰州现有门与 Minimal 示例门共用同一套接口。

### 当前 Runtime

- Movement / Waypoint / A*。
- Actor / Token / Form / Health / Damage / Healing / Combat / Chat。
- Multiplayer、Player User、Actor Ownership、Combat Turn Lock。
- 便携 `app/ + map/` Server Runtime 与 Windows / Linux 启动流程。

## 二、Feature Control Layer 后续

V1.5 首版只实现最小、稳定的 `toggle`。以下内容明确留到后续版本，不继续塞入 V1.5：

### 1. Lock / GM 右键

参考 VTT 门交互增加：

```text
closed ⇄ open
closed ⇄ locked   (GM)
```

- GM 右键切换锁定状态。
- locked 状态阻止普通 Player 打开。
- `locked` 应进入通用 Feature State / Capability，而不是 Door 专属字段。

### 2. Secret / Visibility

- 秘密门、隐藏机关。
- GM 可见 / Player 不可见。
- 根据权限与探索状态决定控件是否渲染。
- 不通过 CSS 假隐藏敏感信息；Server 最终负责可见数据过滤。

### 3. Player Feature Interaction Permission

当前 Player 修改 `featureStates` 会被 World 权限模型阻止。后续正式增加：

```text
permissions.interactFeatures
```

并逐步细分：

```text
open
close
activate
use
```

要求：Server 验证 operation，不允许只靠前端按钮禁用。多人同步长期应从“整份 World Snapshot 比较”升级到明确的 Feature operation / patch。

### 4. 更多通用 Control

在不引入 DoorSystem 的前提下扩展：

- `toggle`：门、吊桥、灯、传送门开关。
- `button`：机关、按钮、一次性触发器。
- `activate / deactivate / use` 等通用 Action。
- MapPackage 自定义 anchor、图标、尺寸和显示策略。
- 状态变化动画、音效与 GM 提示。

## 三、核心架构下一阶段

按当前 V1.5 边界继续推进：

1. **Scene Instance**：MapPackage 作为内容模板，Scene 保存运行实例状态。
2. **Scene Manager Foundation**：切换/加载 Scene，不让单个 app.js 持有全部场景生命周期。
3. **World Model**：World 正式拥有 Actors、Tokens、Scenes、Settings、Users。
4. **World Manager**：World 创建、选择、加载、备份与迁移。
5. **Data Root / Storage Migration**：明确程序文件、World 数据、地图资源和上传资源的持久化边界。
6. **External MapPackage Registry / Import**：允许外部地图包注册、校验和选择。
7. **Single Server / `/setup` Launcher**：统一首次配置和启动入口。

这些阶段不得反向破坏：

```text
MapPackage
  ↓
Feature Capability / State
  ↓
Feature Operations
  ↓
Generic UI / Runtime Adapter
```

## 四、Server / Multiplayer 后续

### Authoritative Operation

逐步把 Client 的完整 World push 改为：

```text
Client Operation
      ↓
Server Permission + Validation
      ↓
World Commit
      ↓
Operation/Patch Broadcast
```

优先覆盖：

- Feature open / close / activate。
- Token movement。
- HP / resource change。
- Scene damage / restore。
- Combat turn actions。

### Permissions

继续完善：

- GM / Player / Observer。
- Actor Ownership。
- Feature Interaction 权限。
- Scene 编辑权限。
- 隐藏 Token / 私密属性。
- Secret Feature / Fog 数据过滤。

### Persistence

短期继续使用可审计 JSON World Store；只有在并发、索引或数据量真正成为瓶颈后再迁移 SQLite。

---

## 五、游戏与 VTT 功能

Server、Scene 和权限稳定后再逐步加入：

- Fog of War / Vision / Light。
- Secret Door / Trap / Exploration State。
- Initiative 与更完整 Combat workflow。
- Dice / Check / Target。
- 状态效果持续时间。
- Scene Notes / Journal。
- 地图声音、环境效果和交互动画。

复杂规则继续放在独立系统，不写死进 MapPackage、Actor 或 Movement。

## 六、内部重构待办

### Actor / Scene Schema

- `location.type = building` 最终迁移为正式 Feature / Scene location schema。
- Token 最终摆脱旧 Character backing model。
- Attack Area anchor 迁移到 Token / Scene Entity。
- 下一代 World schema 必须提供显式迁移器，不能直接删除旧存档兼容。

### App

继续拆分历史大 `app.js`：

```text
AppCore
├─ SceneSystem
├─ EntitySystem
├─ MovementSystem
├─ FeatureInteractionSystem
├─ MeasureSystem
├─ RangeSystem
└─ AppShellUI
```

### Damage / Flood Capability 化

V1.5 已让 Interaction / Navigation 不再按地图 category 决策；后续再把历史 Damage/Flood 几何策略中的 `wall/building` 类别判断逐步迁移为显式 Capability，例如：

```text
damage.mode = object | clip
flood.blocker = true
```

这属于 Engine 深层清理，不作为 V1.5 封版阻断项。

---

## 七、版本与发布原则

- 小修复使用 Patch。
- 完整新功能使用 Minor。
- 不兼容 World / API 变化才考虑 Major。
- 版本提升前必须先确认，不因内部提交次数自动升级。
- 每个 Candidate 必须继续通过 Node tests、JS syntax、source separation、Vite build、Linux runtime smoke、Windows BAT smoke。

当前 V1.5 PR 在正式合并前继续保持 Draft；V1.5 之外的功能优先进入本规划，不在封版阶段继续扩大范围。
