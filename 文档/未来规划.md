# RPGmap 未来规划

当前应用版本：**1.3.0**

目标：把 RPGmap 从当前单机 / 本地服务器模式逐步发展为类似 Foundry VTT 的轻量自托管多人 VTT。项目本身不绑定单一地图；地图继续通过独立 MapPackage 接入，World、Actor、Token、Combat、Health、Chat 等运行状态逐步迁移到 Server 统一管理。

> 说明：本文中的 **v1.4.0** 目前表示下一阶段候选目标，不代表版本号已经正式提升。实际版本提升仍按开发流程，在功能完成并测试通过后单独确认。

---

## 一、当前 1.3.0 基础

### Entity / Actor

- Actor / Token / Form / Runtime / Effects 分层。
- XLSX 角色卡导入，只读取已保存的最终缓存值。
- 技能鉴定、意志 / 反射 / 强韧豁免。
- 21 种不良状态及阈值。
- 多 Form / 变身。

### Movement / Selection / Measurement

- Token 拖动与 Waypoint。
- EasyStar A* 寻路。
- Ghost Token。
- 5 / 10 / 20 / 50 / 100 m 吸附。
- 单选、多选、矩形框选。
- Ruler 自由测距与角色位置起点测距。
- Movement / Ruler 共用高层距离标签。

### Combat / Health / Chat

- Combat Tracker、先攻、拖动排序、轮次与当前回合。
- SimpleHP 与 WoundTrack 两种生命模式。
- Damage / Healing 对所选 Token 应用伤害或恢复。
- Token 常驻生命条。
- Chat / Game Log：普通消息、Combat、Damage、Healing 记录，并预留 Roll 接口。

### Local Server

- Node HTTP Server。
- 默认监听 `0.0.0.0:30000`。
- 本机可访问 `http://127.0.0.1:30000`。
- 同一局域网设备已经可以通过主机的局域网 IP 打开 RPGmap 页面。
- `/api/health`、`/api/version`。
- 预留 `data/worlds`、`data/uploads`、`data/backups`。

当前主要限制：**长期业务状态仍主要保存在各浏览器本地，Server 尚未成为 authoritative state，因此不同浏览器虽然能打开同一个页面，但并不会自动共享同一个游戏状态。**

# 二、下一阶段候选目标：v1.4.0 Multiplayer V1

v1.4.0 的核心目标建议定义为：

> **让一台用户电脑直接作为 RPGmap Host，其他玩家通过局域网或互联网连接到该 Host，并共享同一个 World。**

建议先完成稳定的 LAN Multiplayer，再把相同 Server / WebSocket 架构用于互联网远程联机。

## 2.1 主机模式

```text
GM / Host 电脑
      │
      ├─ RPGmap Server
      ├─ World Store
      ├─ WebSocket
      └─ Browser Client
              │
              ├──────── Player A 浏览器
              ├──────── Player B 浏览器
              └──────── Player C 浏览器
```

主机电脑负责：

- 运行 RPGmap Server。
- 保存 World 数据。
- 校验客户端操作。
- 广播实时状态。
- 保存 Combat / Health / Chat 等共享数据。

玩家电脑原则上只需要浏览器；在直接局域网模式下无需安装 RPGmap。

---

## 2.2 身份模型：只保留 GM / Player

v1.4.0 **不做复杂账号系统**，不引入：

- 注册账号。
- 用户密码库。
- 邮箱。
- OAuth。
- JWT 登录体系。
- 好友 / 社交系统。

RPGmap 内部只区分：

```text
GM
Player
```

建议 Session 结构：

```js
ClientSession {
  id,
  displayName,
  role: "gm" | "player"
}
```

### GM

- 启动 Server 的主机拥有 GM 权限。
- GM 可以控制全部 Actor / Token。
- GM 可以修改 Combat、Health、Scene 等共享状态。
- GM 可以分配角色所有权。

### Player

- 进入游戏时只填写显示名称。
- 可以控制自己拥有的角色。
- 不能执行 GM-only 操作。

### 最小安全凭据

在纯局域网内，可以尽量保持“主机自动 GM、其他连接默认 Player”的简单体验。

如果通过公网访问，则即使仍然不做账号密码，也至少需要一种轻量凭据，例如：

```text
Player Join Code
GM Secret / GM Key
```

它们属于当前 World / Session 的访问凭据，而不是用户账号系统。目的只是避免任何拿到公网 URL 的人都可以自行声明为 GM。

# 三、联机方式

## 3.1 模式 A：同一局域网直接连接

这是 v1.4.0 的第一优先级。

```text
GM：192.168.1.105:30000

Player A → http://192.168.1.105:30000
Player B → http://192.168.1.105:30000
```

优点：

- 架构最简单。
- 延迟低。
- 不需要第三方服务器。
- 玩家只需要浏览器。
- 适合家庭路由器、实验室 LAN、手机热点等环境。

注意：

- Windows 防火墙需要允许 Node.js / RPGmap Server 通过专用网络。
- 部分学校、酒店、公共 Wi-Fi 存在 AP / Client Isolation，同一 Wi-Fi 设备可能不能直接互访。

---

## 3.2 模式 B：虚拟局域网远程联机

这是 **v1.4.0 远程测试最推荐的方式**。

可使用：

- Tailscale。
- ZeroTier。

工作方式：

```text
真实互联网
     │
     ▼
虚拟私有网络
     │
     ├─ GM / Host
     ├─ Player A
     └─ Player B
```

RPGmap 本身仍然按局域网方式工作：

```text
http://<Host 的虚拟网络 IP>:30000
```

优点：

- 不需要开放家庭路由器端口。
- 不需要公网 IPv4。
- 对 NAT / CGNAT 更友好。
- RPGmap Server 不直接暴露给整个互联网。
- 可以继续使用同一套 LAN Server / WebSocket 代码。

代价：

- GM 和玩家通常都需要安装并加入相同虚拟网络。
- 第三方虚拟网络本身可能有独立的设备登录 / 授权流程，但这与 RPGmap 的 GM / Player 身份系统分离。

因此：**RPGmap 本身仍只做 GM / Player，不因此引入 RPGmap 账号体系。**

---

## 3.3 模式 C：公网 Tunnel，玩家浏览器直接访问

后续可实验支持：

- Cloudflare Tunnel。
- Tailscale Funnel 等公网 Tunnel。

示意：

```text
Player Browser
      │
      ▼ HTTPS
Public Tunnel
      │
      ▼
RPGmap Host:30000
```

优点：

- 玩家可以只使用浏览器。
- 主机通常不需要手动做路由器端口映射。
- 可以拥有 HTTPS 公网地址。

但这种模式意味着 RPGmap 已经面向公网，因此必须至少具备：

- Player Join Code。
- GM Secret / GM Key。
- Server-side 权限检查。
- WebSocket Origin / Host 检查。
- 基础 Rate Limit。
- 上传大小限制。
- 路径遍历防护。
- 安全响应头。

在这些最小安全措施完成前，**公网 Tunnel 只能作为实验模式，不作为默认正式玩法。**

---

## 3.4 模式 D：家庭路由器直接端口转发

技术上可行：

```text
Internet
   ↓
Public IP:30000
   ↓ Port Forward
Host PC:30000
```

但不建议作为 RPGmap 默认方案，原因包括：

- 部分宽带没有公网 IPv4。
- CGNAT 下无法直接端口映射。
- 路由器配置差异大。
- Windows 防火墙 / NAT 问题多。
- 直接暴露服务端口需要更严格的安全措施。

如果将来支持真正公网自托管，优先考虑 Tunnel 或 VPS + HTTPS 反向代理，而不是要求普通用户手工配置端口转发。

# 四、Server Authoritative State

v1.4.0 最大的架构变化不是“打开 WebSocket”，而是：

> **Server 必须成为共享游戏状态的唯一真实数据源。**

数据流：

```text
Client Action
     ↓
Server Validate
     ↓
World State Update
     ↓
Persist
     ↓
WebSocket Broadcast
     ↓
All Connected Clients
```

例如 Token 移动：

```text
Player 拖动 Token
        ↓
Client 本地预览
        ↓
token.move
        ↓
Server 检查角色所有权
        ↓
更新 Token 坐标
        ↓
广播 token.updated
        ↓
GM / 所有 Player 同步
```

Client 可以继续做拖动 / 路线等局部预测，但最终共享坐标由 Server 确认。

---

# 五、Shared State 与 Local UI State

## 5.1 必须同步到 Server

### Actor

- Current Form。
- HP / WoundTrack。
- 精力。
- 意志。
- 不良状态当前值。
- Runtime / Effects 中明确需要共享的部分。

### Token

- 创建 / 删除。
- 地图位置。
- 当前 Form / Appearance。
- hidden / locked。
- 与 Actor 的关联。

### Combat

- Combat 是否存在 / 是否开始。
- 参战者。
- Initiative。
- 手动顺序。
- Round。
- 当前 Turn。

### Chat / Game Log

- 普通消息。
- Combat Log。
- Damage Log。
- Healing Log。
- 后续 Roll / Check 消息。

### Scene

- 需要永久保存的场景破坏 / 恢复。
- 当前 Scene / Map。
- 未来 GM-only 场景状态。

---

## 5.2 保持浏览器本地，不同步

以下属于个人 UI 状态：

- Selection。
- Ruler。
- Mouse Hover。
- 当前 Inspector。
- 打开的角色卡窗口。
- 地图缩放。
- 地图视角中心。
- 本地面板展开 / 收起状态。

原则：

```text
Shared Game State → Server
Local Interaction State → Browser
```

例如 Player A 框选某个 Token，不应该导致 GM 和 Player B 也选中该 Token。

# 六、World Store V1

v1.4.0 初期不急于引入数据库，JSON World Store 足够。

建议：

```text
data/
└─ worlds/
   └─ <world-id>/
      ├─ manifest.json
      ├─ actors.json
      ├─ tokens.json
      ├─ scenes.json
      ├─ combat.json
      ├─ chat.json
      ├─ settings.json
      ├─ uploads/
      └─ backups/
```

要求：

- 原子写入。
- 自动备份。
- World 数据和程序版本分离。
- 更新 RPGmap 不应删除用户 World。
- 重新导入角色 Base 数据不得无条件覆盖 Runtime。

服务器启动时加载 World；Client 连接后从 Server 获取当前完整 Snapshot。

# 七、WebSocket / Action Protocol V1

建议使用统一 Action / Event 协议，不让每个子系统自行定义独立网络层。

客户端请求示例：

```js
{
  type: "token.move",
  requestId: "...",
  payload: {
    tokenId: "token-001",
    x: 1234,
    y: 846
  }
}
```

伤害：

```js
{
  type: "actor.damage",
  payload: {
    actorId: "actor-001",
    amount: 7,
    damageType: "L"
  }
}
```

聊天：

```js
{
  type: "chat.send",
  payload: {
    content: "我调查房间。"
  }
}
```

战斗：

```js
{
  type: "combat.nextTurn"
}
```

服务器广播统一 Event：

```text
Action
  ↓
Validate Permission
  ↓
Apply Domain Logic
  ↓
Persist World
  ↓
Broadcast Event
```

后续 Dice / Check 也直接接入同一协议和 ChatSystem。

# 八、角色所有权与权限

v1.4.0 虽然不做账号体系，但第一版就应该有角色所有权。

例如：

```text
Player A
owns → 银

Player B
owns → 陈某
```

Player A：

- 可以移动“银”的 Token。
- 可以修改“银”允许玩家修改的资源。
- 不可以移动 Player B 的角色。

GM：

- 可以控制所有角色。
- 可以修改所有 Combat / Scene 状态。
- 可以改变角色所有权。

**权限检查必须由 Server 执行。**

不能仅通过隐藏前端按钮实现权限，因为玩家可以自行构造网络请求。

---

# 九、断线与重连

v1.4.0 第一版优先保证稳定，不急于实现复杂 Event Replay。

建议：

```text
WebSocket 断线
     ↓
自动重连
     ↓
请求最新 World Snapshot
     ↓
替换共享状态
     ↓
继续接收实时 Event
```

以后如果 World / Chat 数据规模明显增大，再增加：

- revision。
- sequence number。
- missed-event recovery。
- incremental snapshot。

# 十三、版本与发布策略

应用版本统一使用 `MAJOR.MINOR.PATCH`。

- Patch：Bug 修复、小型兼容修正。
- Minor：新增完整功能 / 子系统，例如 Multiplayer V1。
- Major：不兼容存档、World Schema、协议或核心架构变化。

版本提升必须先说明理由并得到明确确认，再修改版本号与 `文档/工作日志.md`。

GitHub Release 使用：

```text
v1.3.0
v1.3.1
v1.4.0
```

开发、测试和发布流程遵守 `文档/开发说明.md`。

# 十四、当前推荐开发顺序

1. 以 1.3.0 `main` 为基线设计 Multiplayer V1 网络协议。
2. 建立 Server-side World Store V1。
3. 增加 ClientSession：GM / Player。
4. 建立 WebSocket 连接、Snapshot 与广播机制。
5. 首先同步 Token 移动。
6. 再同步 Actor / Health / Damage / Healing。
7. 同步 Combat。
8. 同步 Chat / Game Log。
9. 增加角色 Ownership 与 Server 权限校验。
10. 完成断线重连。
11. 在真实局域网进行多设备测试。
12. 使用 Tailscale / ZeroTier 进行跨互联网远程测试。
13. 评估 Cloudflare Tunnel / Tailscale Funnel 的浏览器直连实验模式。
14. 功能稳定后再提出是否正式提升到 1.4.0。

不要在 Multiplayer V1 之前引入复杂账号体系、数据库、微服务或完整公网平台。
