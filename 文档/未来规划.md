# RPGmap 未来规划

当前开发版本：**V1.4.3 Candidate**  
当前稳定 `main`：**V1.4.0**

目标：把 RPGmap 逐步发展为类似 Foundry VTT 的自托管、可携带、可扩展 VTT 平台，并保持程序、地图资源和 World 运行状态相互分离。

状态标记：

- ✅ **已实现**：当前 Candidate 已具备并进入自动测试。
- 🟨 **部分实现**：核心基础已经存在，但完整管理能力尚未完成。
- ⬜ **计划中**：尚未开始正式实现。
- 🧭 **Launcher 已预留入口**：Launcher UI 已保留位置，后续可直接扩展。
- ↩️ **已撤回方案**：曾实现/测试，但不再作为当前推荐架构。

## 二、当前总体架构

```text
启动 RPGmap.bat
      ↓
Node.js
      ↓
RPGmap Web Launcher
├─ Dynamic Loopback Port
├─ Local / LAN / Internet Lifecycle
├─ GM Admin Session
├─ Connection Dashboard
├─ Logs
└─ Future Managers
    ├─ World Manager
    ├─ Scene Manager
    └─ Backup Center

RPGmap Game Server :30000
├─ HTTP / Static Client
├─ World Store
├─ WebSocket
├─ Player Identity
├─ Actor Ownership
└─ Combat Turn Authority

Portable Package
├─ app/        程序前端
├─ world/      当前 Campaign 运行状态
├─ maps/       Map / Scene 资源库
└─ tools/      cloudflared / 未来 Portable Node
```

长期原则：

1. Server 是共享 World 的最终数据与权限裁决者。
2. Client 负责输入、显示和友好预检。
3. Launcher 负责本机 GM 的启动、网络、User 与未来 World/Scene/Backup 管理。
4. `app/` 可以升级替换，但不能破坏 `world/` / `maps/`。
5. `maps/` 只描述地图 / Scene **是什么**。
6. `world/` 描述当前游戏里**发生了什么**。
7. 不为了桌面外观增加不必要启动层；当前优先保证 BAT + Web Launcher 稳定、透明、可诊断。

# 六、持久化与数据库 — ⬜ 暂缓

JSON World Store 当前仍足够。

只有出现明显瓶颈后再考虑 SQLite，例如：

- World 数据量显著增大；
- operation / audit log 很长；
- 多 World / 多 Scene 查询复杂；
- 原子 JSON 重写成为明确性能问题。

在此之前，不为了技术栈复杂度提前引入数据库。

