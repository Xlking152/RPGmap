# RPGmap 未来规划

当前开发基线：**V1.5.0 Candidate**。

目标：在已经完成的 MapPackage / Feature Capability / Feature State / Feature Operations 分层上，继续把 RPGmap 发展为类似 Foundry VTT 的自托管 Web 跑团平台。后续功能必须沿用“地图描述内容，Core 执行规则”的边界，不再把地图类别或单张地图逻辑写回通用系统。

## 一、V1.5 已完成基础

### MapPackage / Reference Map

- 兰州城已整理为 Reference MapPackage。
- Runtime 不读取 `reference/`，地图在 build 时打进客户端。
- Layer Plan、Feature ID、Capability、Navigation effect、taxonomy 已有统一契约。
- Minimal Reference Map 用于验证 Core 不依赖兰州类别。
- 源码独立性测试限制兰州 Reference import 只能存在于默认地图 build adapter 与明确的历史 compatibility shim；Engine / Movement / Interaction / Elevation 禁止出现兰州 Feature ID。

### Feature Interaction

- 统一 Feature State：`open / intact|partial|destroyed / custom`。
- 统一 Feature Operations：`inspect / enter / exit / damage / restore / open / close`。
- Generic Feature UI 不再依赖 `building / gate` 等地图类别。
- Open / Close 已与 Navigation、SVG、Save、Multiplayer World State 接通。
- V1.5 新增通用 **Feature Control Layer**：openable Feature 可在地图上通过小型 FVTT 风格门控件直接点击开关；destroyed 后控件隐藏；兰州现有门与 Minimal 示例门共用同一套接口。

### Navigation / 阻挡验证

- Navigation 支持通用 `blockingPolygon` 与 `passagePolygon`，将关闭阻挡区和开启通行廊道与 Feature 视觉几何分离。
- 兰州四座城门关闭时，阻挡带跨过完整门洞并与城墙端部重叠，避免 10 m A* 栅格从门楼两侧漏过。
- 回归测试直接调用实际 `findNavigationPath()` / EasyStar，而非只检查网格值。
- 通用障碍关闭时 EasyStar 必须返回无路径，Movement waypoint planner 必须返回 `valid: false`；打开或高度越过后路径恢复。
- 兰州北/东/南/西四门分别验证关闭无局部穿越路径、开启恢复通路。
- 四城门全部关闭时，城外到城中心的全图路径不存在；打开北门后全图路径恢复。

### 2.5D Elevation / Height Blocking

- Token Runtime 增加 `elevationFt`，语义为“当前离地高度”，默认 `0 ft`。
- Feature Navigation Capability 增加 `blockingHeightFt`，语义为“障碍顶部阻挡高度”。
- 通行规则统一为：`elevationFt > blockingHeightFt` 时忽略该 Feature 障碍；等高仍然阻挡。
- 未声明 `blockingHeightFt` 的旧 Feature 继续按传统无限高度二维障碍处理，保证旧地图不被静默改变。
- Token 顶部显示 Elevation，底部显示 HP Bar。
- 右键 Token 可打开紧凑 Elevation HUD；多人模式继续服从 Actor OWNER / Combat Turn Lock。
- 通用 Feature Inspector 可编辑阻挡高度；运行时修改进入 `Feature State.custom`，不回写 MapPackage。
- 新角色放置会强制使用 `0 ft` ground mover context，避免继承上一个高空 Token 的越障能力。
- 当前高度只影响 Feature Navigation obstacle；水体、弹坑、洪水仍保持原二维语义。

### 当前 Runtime

- Movement / Waypoint / A*。
- Actor / Token / Form / Health / Damage / Healing / Combat / Chat。
- Multiplayer、Player User、Actor Ownership、Combat Turn Lock。
- 便携 `app/ + map/` Server Runtime 与 Windows / Linux 启动流程。

## 二、Feature Control Layer 后续

V1.5 首版只实现最小、稳定的 `toggle`。以下内容明确留到后续版本，不继续塞入 V1.5：

### 1. Lock / GM 右键

参考 VTT 门交互增加：

```text
closed ⇄ open
closed ⇄ locked   (GM)
```

- GM 右键切换锁定状态。
- locked 状态阻止普通 Player 打开。
- `locked` 应进入通用 Feature State / Capability，而不是 Door 专属字段。

### 2. Secret / Visibility

- 秘密门、隐藏机关。
- GM 可见 / Player 不可见。
- 根据权限与探索状态决定控件是否渲染。
- 不通过 CSS 假隐藏敏感信息；Server 最终负责可见数据过滤。

### 3. Player Feature Interaction Permission

当前 Player 修改 `featureStates` 会被 World 权限模型阻止。后续正式增加：

```text
permissions.interactFeatures
```

并逐步细分：

```text
open
close
activate
use
```

要求：Server 验证 operation，不允许只靠前端按钮禁用。多人同步长期应从“整份 World Snapshot 比较”升级到明确的 Feature operation / patch。

### 4. 更多通用 Control

在不引入 DoorSystem 的前提下扩展：

- `toggle`：门、吊桥、灯、传送门开关。
- `button`：机关、按钮、一次性触发器。
- `activate / deactivate / use` 等通用 Action。
- MapPackage 自定义 anchor、图标、尺寸和显示策略。
- 状态变化动画、音效与 GM 提示。

## 三、Elevation / 2.5D 后续计划

V1.5 只建立“Token 离地高度 vs Feature 阻挡顶部高度”的基础模型。以下能力明确放到后续版本，不继续扩大本轮范围：

### 1. 地形海拔 / Ground Elevation

当前 `elevationFt` 是离地高度，地图地面仍视为统一零平面。未来需要区分：

```text
groundElevationFt
+
tokenElevationFt (relative)
=
absoluteElevationFt
```

用于山地、城台、屋顶、地下区域和有高度差的 Scene。

### 2. Floors / 多层空间

- 建筑楼层。
- 地下层 / 地面层 / 屋顶层。
- 楼梯、电梯、梯子等层间连接。
- Scene / Token 所在层与高度联合判定。

楼层不应简单塞入 `location.type = building`，应与后续 Scene Instance / Scene Location Schema 一起设计。

### 3. 桥上 / 桥下双层通行

未来桥梁需要同时表达：

```text
桥面通道
桥下通道
桥体阻挡区间
```

不能只靠当前二维 `bridgeFeatureIds` 解决；应发展为高度区间或多层 Navigation Surface。

### 4. 飞行与垂直移动成本

- 上升 / 下降距离。
- 飞行移动消耗。
- 垂直速度。
- 不同 Movement Mode（walk / fly / climb / swim）。

未来 Navigation Query 应继续扩展 `moverContext`，而不是为飞行角色复制一套 Pathfinding。

### 5. 坠落 / Fall

- 高度突然降低。
- 坠落距离。
- 坠落伤害。
- 着陆与悬停状态。

具体伤害规则应进入独立规则系统，不写死进 Navigation。

### 6. Vision / LOS / Projectile Height

- 观察者视点高度。
- 障碍遮挡高度。
- 高处观察越过低墙。
- 远程攻击 / 投射物是否越过障碍。
- Fog / Vision 的垂直可见性。

这部分应与未来 Fog of War / Vision / Light 一起实现。

### 7. Token Physical Height / Volume

当前只有 Token 的“离地高度”，没有身体顶部高度。未来可引入：

```text
tokenBaseElevationFt
tokenPhysicalHeightFt
```

用于大型生物、趴伏、飞行体积、门洞净高等规则。

### 8. 水体 / 弹坑 / 洪水垂直语义

V1.5 中这些仍然按二维规则阻挡。未来再定义：

- 飞行 Token 是否忽略水体。
- 弹坑深度。
- 洪水水位。
- 游泳 / 船只 / 飞行的不同通行条件。

### 9. Mover Context 显式化

当前 V1.5 为兼容历史 `engine/app.js`，通过 Elevation Runtime Adapter 向旧 Navigation 调用提供当前 mover context，并对旧“放置角色”UI 提供 ground-placement compatibility guard。

未来 App / Scene 拆分后，目标接口应明确变为：

```text
NavigationQuery
├─ scene
├─ mover/token
├─ movementMode
├─ elevation
└─ permissions/rules
```

由调用方显式传入，最终删除兼容型全局 Runtime Context 与 placement guard。

## 四、核心架构下一阶段

按当前 V1.5 边界继续推进：

1. **Scene Instance**：MapPackage 作为内容模板，Scene 保存运行实例状态。
2. **Scene Manager Foundation**：切换/加载 Scene，不让单个 app.js 持有全部场景生命周期。
3. **World Model**：World 正式拥有 Actors、Tokens、Scenes、Settings、Users。
4. **World Manager**：World 创建、选择、加载、备份与迁移。
5. **Data Root / Storage Migration**：明确程序文件、World 数据、地图资源和上传资源的持久化边界。
6. **External MapPackage Registry / Import**：允许外部地图包注册、校验和选择。
7. **Single Server / `/setup` Launcher**：统一首次配置和启动入口。

这些阶段不得反向破坏：

```text
MapPackage
  ↓
Feature Capability / State
  ↓
Feature Operations
  ↓
Generic UI / Runtime Adapter
```

## 五、Server / Multiplayer 后续

### Authoritative Operation

逐步把 Client 的完整 World push 改为：

```text
Client Operation
      ↓
Server Permission + Validation
      ↓
World Commit
      ↓
Operation/Patch Broadcast
```

优先覆盖：

- Feature open / close / activate。
- Feature blocking-height World override。
- Token movement / elevation change。
- HP / resource change。
- Scene damage / restore。
- Combat turn actions。

### Permissions

继续完善：

- GM / Player / Observer。
- Actor Ownership。
- Feature Interaction 权限。
- Feature World Property 编辑权限。
- Scene 编辑权限。
- 隐藏 Token / 私密属性。
- Secret Feature / Fog 数据过滤。

### Persistence

短期继续使用可审计 JSON World Store；只有在并发、索引或数据量真正成为瓶颈后再迁移 SQLite。

## 六、游戏与 VTT 功能

Server、Scene 和权限稳定后再逐步加入：

- Fog of War / Vision / Light。
- Secret Door / Trap / Exploration State。
- Initiative 与更完整 Combat workflow。
- Dice / Check / Target。
- 状态效果持续时间。
- Scene Notes / Journal。
- 地图声音、环境效果和交互动画。

复杂规则继续放在独立系统，不写死进 MapPackage、Actor 或 Movement。

## 七、内部重构待办

### Actor / Scene Schema

- `location.type = building` 最终迁移为正式 Feature / Scene location schema。
- Token 最终摆脱旧 Character backing model。
- Attack Area anchor 迁移到 Token / Scene Entity。
- 下一代 World schema 必须提供显式迁移器，不能直接删除旧存档兼容。

### App

继续拆分历史大 `app.js`：

```text
AppCore
├─ SceneSystem
├─ EntitySystem
├─ MovementSystem
├─ FeatureInteractionSystem
├─ ElevationSystem
├─ MeasureSystem
├─ RangeSystem
└─ AppShellUI
```

V1.5 仍保留三个有意的兰州源码适配入口：默认地图 build adapter、兰州历史 import shim、presentation 历史 shim。它们不参与 Runtime 规则。完成 AppCore / External MapPackage Registry 后应逐步删除兼容 shim，并把默认地图选择从编译期适配器升级为正式 Registry。

### Damage / Flood Capability 化

V1.5 已让 Interaction / Navigation 不再按地图 category 决策；后续再把历史 Damage/Flood 几何策略中的 `wall/building` 类别判断逐步迁移为显式 Capability，例如：

```text
damage.mode = object | clip
flood.blocker = true
```

这属于 Engine 深层清理，不作为 V1.5 封版阻断项。

---

## 八、版本与发布原则

- 小修复使用 Patch。
- 完整新功能使用 Minor。
- 不兼容 World / API 变化才考虑 Major。
- 版本提升前必须先确认，不因内部提交次数自动升级。
- 每个 Candidate 必须继续通过 Node tests、JS syntax、source separation、Vite build、Linux runtime smoke、Windows BAT smoke。

当前 V1.5 PR 在正式合并前继续保持 Draft；V1.5 之外的功能优先进入本规划，不在封版阶段继续扩大范围。
