# RPGmap 未来规划

> 目标：逐步把当前 RPGmap 从单机 Vite 前端工具，演进为类似 Foundry VTT 的自托管 Web 应用。服务器负责长期运行、世界数据保存、权限与多人同步；GM 与玩家均通过浏览器访问。

## 一、当前已完成基础

### 1. MovementSystem
- Token 直接拖动规划移动。
- Waypoint 分段路径。
- Ctrl/Cmd、F、Alt+F、右键、Enter、Esc 等移动快捷操作。
- EasyStar A* 路径规划。
- Ghost Token 预览。
- 5 / 10 / 20 / 50 / 100 m 吸附与移动计价。
- 自动吸附档位与规划中滚轮切换。

### 2. EntitySystem
- Actor / Token 两层模型。
- Actor 保存身份、头像、Forms、Base / Runtime / Effects、资源、属性、技能 / 豁免。
- Token 保存地图实例关系并与 MovementSystem 衔接。
- XLSX 角色卡导入只读取 `角色概览` 与 `具体数值表` 的最终缓存值。
- HP、精力、意志、自定义特殊能量槽可实时修改。
- 多 Form 与 V 快捷切换形态。
- 攻击 / 防御保留扩展接口。

### 3. AppShell UI
- 顶层 UI 收口为选择、测量、范围、场景、导入角色、存档。
- 角色库 / 当前对象双侧栏入口。
- Token 右键菜单。
- Movement HUD / 状态栏。
- Marker 已从新 UI 与新数据模型退出。

---

## 二、总架构目标

```text
RPGmap Server
│
├─ HTTP Server
│  ├─ 提供编译后的 Web Client
│  └─ REST API
│
├─ World Store
│  ├─ Actors
│  ├─ Tokens
│  ├─ Scenes
│  ├─ Assets
│  └─ Backups
│
├─ Realtime
│  └─ WebSocket
│
└─ Authentication / Permissions
   ├─ GM
   └─ Player

        ↓ HTTP / WebSocket

Browser Client
├─ MovementSystem
├─ EntitySystem
├─ AppShell UI
├─ Measure / Range / Scene
└─ Future CombatSystem
```

核心原则：

1. Server 最终成为 authoritative state，浏览器不再是唯一真实数据源。
2. Client 负责显示、输入与局部预测；最终写入由 Server 验证并保存。
3. World 数据、上传资源和备份必须与程序版本分离，升级应用不能破坏用户数据。
4. 发布包不依赖 `.exe`，以 Node 自托管包和 Docker 镜像为主要交付方式。

## 三、阶段规划

## Phase S0：本地服务器测试包（当前阶段）

目的：先让开发期测试方式变成“启动服务器 → 浏览器访问”，不再依赖 `vite dev`。

### 功能
- 使用 Node.js 启动本地 HTTP Server。
- 默认端口 `30000`。
- `HOST=0.0.0.0`，允许局域网访问。
- 提供编译后的前端静态文件。
- SPA fallback 到 `index.html`。
- `/api/health`。
- `/api/version`。
- 自动建立：
  - `data/worlds/`
  - `data/uploads/`
  - `data/backups/`
- Windows 一键启动 `.bat`。
- Linux/macOS 一键启动 `.sh`。

### 清洁发布要求
发布包不得包含：
- `.git/`
- `node_modules/`
- npm cache
- 测试目录
- Playwright / 浏览器测试输出
- `dist/` 历史残留
- 临时构建目录
- Windows / 搜狗等外部垃圾文件
- 历史参考资料

首次构建时依赖安装到系统临时目录，构建完成后删除临时目录。部署目录只保留源码副本、`public/`、`data/`、服务器和启动脚本。

### 数据状态
本阶段继续允许现有 localStorage 工作，不立即迁移业务数据到 Server。

---

## Phase S1：正式 RPGmap Server V1

目的：建立真正独立于 Vite 的生产服务器层。

建议技术：Node.js + Fastify。

目录目标：

```text
server/
├─ index.js
├─ config.js
├─ api/
├─ storage/
└─ realtime/
```

### 功能
- Fastify 静态文件服务。
- Server 配置：HOST / PORT / DATA_DIR。
- Health / Version API。
- 统一错误处理与日志。
- 应用版本、Build Commit、World 信息输出。
- 正式 `npm start`。
- `npm run package:server` 生成干净 Server ZIP。

---

## Phase S2：World Store

目的：把 localStorage 中的长期状态迁移到服务器文件系统。

初期优先使用 JSON 文件，不急于引入数据库。

建议：

```text
data/
└─ worlds/
   └─ <world-id>/
      ├─ manifest.json
      ├─ actors.json
      ├─ tokens.json
      ├─ scene.json
      ├─ settings.json
      ├─ uploads/
      └─ backups/
```

### 迁移内容
- Actor / Forms / Runtime / Effects。
- Token。
- Scene Events。
- 地图状态。
- 上传头像和未来自定义地图资源。

### 原则
- Excel 文件本身不必上传到 Server；浏览器解析后提交标准 Actor JSON。
- 当前 HP / 精力 / 意志等 Runtime 状态不得因重新导入 Base 数据而被覆盖。
- Server 自动备份 World 数据。
- 写入使用临时文件 + 原子替换，避免断电造成 JSON 半写入。

---

## Phase S3：REST API

建议 API：

```text
GET    /api/worlds
POST   /api/worlds
GET    /api/worlds/:id

GET    /api/worlds/:id/actors
POST   /api/worlds/:id/actors
PATCH  /api/worlds/:id/actors/:actorId

GET    /api/worlds/:id/tokens
POST   /api/worlds/:id/tokens
PATCH  /api/worlds/:id/tokens/:tokenId
DELETE /api/worlds/:id/tokens/:tokenId

GET    /api/worlds/:id/scenes
PATCH  /api/worlds/:id/scenes/:sceneId
```

Client 后续通过 Repository / DataSource 层访问 Server，避免 UI 直接写 fetch。

---

## Phase S4：Realtime / WebSocket

目的：进入真正多人 VTT 架构。

### 第一批同步事件
- Token 移动。
- Token Form 切换。
- HP / 精力 / 意志变化。
- 自定义资源变化。
- Token 创建 / 删除。
- Scene damage / restore。

数据流：

```text
Client Request
    ↓
Server Validate
    ↓
World Store Commit
    ↓
WebSocket Broadcast
    ↓
All Connected Clients
```

### 注意
MovementSystem 可以保留客户端路线预览，但最终 Token 坐标由 Server 确认。

---

## Phase S5：GM / Player 与权限

### 用户角色
- GM
- Player
- Observer（可选）

### 权限方向
- Actor 所有权。
- Token 移动权限。
- 资源修改权限。
- 隐藏 Token。
- GM-only Scene 操作。
- 私密 Actor 信息。
- 玩家可见属性过滤。

Server 必须执行权限检查，不能只在前端隐藏按钮。

---

## Phase S6：多人游戏功能

在 Server / Permission 稳定后逐步增加：
- Target / 目标选择。
- Initiative / 战斗轮次。
- CombatSystem。
- 攻击 / 防御正式模型。
- 状态效果与持续回合。
- 战争迷雾。
- 视野与可见性。
- 玩家私有信息。
- Dice / Check 消息流。
- Chat / System Log（如需要）。

---

## Phase S7：持久化升级

当 JSON World Store 成为瓶颈后再考虑 SQLite。

可迁移：
- Actors
- Tokens
- Users
- Permissions
- Combat state
- Audit log

大文件继续保留文件系统存储：
- Token / Actor 图片
- 地图
- 上传附件

## Phase S8：正式发布

### ZIP Server

```text
RPGmap-Server-vX.Y.Z/
├─ server/
├─ public/
├─ data/
├─ package.json
├─ package-lock.json
├─ start.bat
└─ start.sh
```

### Docker

```text
docker run \
  -p 30000:30000 \
  -v ./rpgmap-data:/app/data \
  rpgmap/server
```

原则：程序镜像和 World 数据完全分离。

## Phase S9：公网部署

推荐：

```text
Internet
   ↓ HTTPS
Caddy / Nginx
   ↓
RPGmap :30000
```

### 必须完成
- HTTPS。
- 登录与 Session。
- CSRF / Origin / WebSocket Origin 策略。
- 上传大小限制。
- 路径遍历防护。
- Rate limit。
- 安全响应头。
- World 定期备份。

不建议直接把裸 Node 端口作为长期公网服务。

## 四、应用内部后续重构

Server 化过程中同时逐步完成：

### Entity
- Token 不再依赖旧 Character backing model。
- `characters` 最终从正式 state schema 删除。
- 旧 Marker 内部实现彻底移除。
- Attack Area anchor 迁移到 Token。

### App API
由当前大 `app.js` 逐步拆为：

```text
AppCore
├─ EntitySystem
├─ MovementSystem
├─ SceneSystem
├─ MeasureSystem
├─ RangeSystem
└─ AppShellUI
```

### DataSource
增加统一数据接口：

```text
LocalDataSource
ServerDataSource
```

开发期仍可运行单机模式；Server 模式切换到 ServerDataSource。

---

## 五、建议优先级

当前推荐顺序：

1. S0 本地服务器测试包。
2. 完成当前 Movement / Entity / UI 的人工体验验证。
3. S1 正式 Server 层。
4. S2 World Store。
5. S3 REST API。
6. S4 WebSocket。
7. S5 权限。
8. Combat / Fog / Chat 等多人玩法。
9. Docker / 公网部署。

不要在 S2 之前过早引入复杂数据库、账号系统或微服务。
