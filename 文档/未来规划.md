# RPGmap 未来规划

当前应用版本：**1.2.0**

目标：把 RPGmap 从当前单机 / 本地服务器过渡阶段，逐步发展为类似 Foundry VTT 的自托管 Web 应用。项目本身不绑定单一地图，未来应支持多个 MapPackage、World、Scene、GM / Player 权限和多人同步。

## 一、当前基础

### MovementSystem

- Token 直接拖动移动。
- Waypoint 分段路线。
- EasyStar A* 寻路。
- Ghost Token。
- 5 / 10 / 20 / 50 / 100 m 吸附。
- 分段距离 / 总距离。

### EntitySystem

- Actor / Token 两层模型。
- Forms / 变身。
- Base / Runtime / Effects。
- HP、精力、意志与自定义资源。
- XLSX 角色卡导入。
- 技能 / 豁免基础数据。

### AppShell UI

- 选择 / 测量 / 范围 / 场景 / 导入角色 / 存档。
- 角色库与当前对象 Inspector。
- Token 右键菜单。
- Movement HUD 与底部状态栏。

### Local Server

- Node HTTP Server。
- 默认端口 `30000`。
- 本地 / 局域网浏览器访问。
- `/api/health`、`/api/version`。
- 预留 `data/worlds`、`data/uploads`、`data/backups`。

当前长期业务状态仍主要保存在浏览器；Server 尚未成为 authoritative state。

---

## 二、总体目标架构

```text
RPGmap Server
├─ HTTP / Static Client
├─ World Store
├─ REST API
├─ WebSocket
├─ Authentication
└─ Permissions
        │
        ▼
Browser Client
├─ AppShell UI
├─ EntitySystem
├─ MovementSystem
├─ Scene / Measure / Range
└─ Future CombatSystem
```

原则：

1. Server 最终成为真实数据源。
2. Client 负责输入、显示和局部预测。
3. World 数据必须与程序版本分离，升级应用不能破坏用户数据。
4. 地图通过 MapPackage / Scene 接入，不复制应用代码。
5. ZIP Server 和 Docker 是主要部署方式，不以桌面 `.exe` 为核心。

## 三、下一阶段优先级

## Phase 1：多地图 / World 基础

这是 RPGmap 从“第一张验证地图”走向通用工具的重要一步。

目标：

- 建立 Map Registry。
- 一个安装可以加载多个 MapPackage。
- World 记录使用哪张地图 / 哪些 Scene。
- MapPackage 只描述地图内容，不承担 Actor / Movement / UI 逻辑。
- 北宋兰州变成普通的第一张内置 / 示例地图。

建议结构：

```text
src/maps/
├─ registry.js
├─ lanzhou.js
└─ <future-map>.js
```

未来 World：

```text
World
├─ Actors
├─ Tokens
├─ Scenes
└─ Settings
```

---

## Phase 2：正式 Server V1

从当前零依赖静态 HTTP Server 升级为正式后端层。

建议：Node.js + Fastify。

```text
server/
├─ index.js
├─ config.js
├─ api/
├─ storage/
└─ realtime/
```

功能：

- HOST / PORT / DATA_DIR 配置。
- 静态 Web Client。
- Health / Version API。
- 统一错误处理与日志。
- 正式 `npm start`。
- 应用版本、Commit、World 信息输出。

---

## Phase 3：World Store

把长期状态从 localStorage 迁移到 Server。

初期使用 JSON 文件即可，不急于引入数据库：

```text
data/
└─ worlds/
   └─ <world-id>/
      ├─ manifest.json
      ├─ actors.json
      ├─ tokens.json
      ├─ scenes.json
      ├─ settings.json
      ├─ uploads/
      └─ backups/
```

需要迁移：

- Actor / Forms / Runtime / Effects。
- Token。
- Scene Events。
- 当前地图 / Scene。
- 上传头像与未来自定义地图资源。

要求：

- 原子写入。
- 自动备份。
- 重新导入角色 Base 数据不得无条件覆盖 Runtime。

---

## Phase 4：REST API

建议：

```text
GET/POST /api/worlds
GET/PATCH /api/worlds/:id

GET/POST/PATCH /api/worlds/:id/actors
GET/POST/PATCH/DELETE /api/worlds/:id/tokens
GET/PATCH /api/worlds/:id/scenes
```

Client 增加统一 DataSource / Repository 层，UI 不直接散落 `fetch()`。

```text
LocalDataSource
ServerDataSource
```

---

## Phase 5：Realtime / WebSocket

第一批同步：

- Token 移动。
- Form 切换。
- HP / 精力 / 意志变化。
- 自定义资源变化。
- Token 创建 / 删除。
- Scene damage / restore。

数据流：

```text
Client Request
      ↓
Server Validate
      ↓
World Store Commit
      ↓
WebSocket Broadcast
      ↓
Connected Clients
```

Movement 可以继续在客户端实时预览，但最终坐标由 Server 确认。

---

## Phase 6：GM / Player 权限

角色：

- GM
- Player
- Observer（可选）

权限：

- Actor 所有权。
- Token 移动权限。
- 资源修改权限。
- 隐藏 Token。
- GM-only 场景操作。
- 私密属性。
- 玩家可见数据过滤。

权限检查必须在 Server 执行，不能只隐藏前端按钮。

---

## Phase 7：游戏系统扩展

Server 和权限稳定后再逐步加入：

- CombatSystem。
- 攻击 / 防御正式模型。
- Initiative / 回合。
- 状态效果持续时间。
- Dice / Check 消息。
- Target。
- 战争迷雾。
- 视野 / 可见性。
- 玩家私有信息。
- Chat / System Log（确有需要时）。

现阶段不要过早把复杂战斗规则写死进 Actor 或 Movement。

---

## Phase 8：持久化升级

只有当 JSON World Store 明显成为瓶颈后再考虑 SQLite。

适合迁移进数据库：

- Actors
- Tokens
- Users
- Permissions
- Combat state
- Audit log

地图、图片和大附件继续使用文件系统。

---

## Phase 9：正式部署

### ZIP Server

```text
RPGmap-Server-vX.Y.Z/
├─ server/
├─ public/
├─ data/
├─ start-rpgmap.bat
└─ start-rpgmap.sh
```

### Docker

```text
docker run \
  -p 30000:30000 \
  -v ./rpgmap-data:/app/data \
  rpgmap/server
```

程序镜像与 World 数据完全分离。

### 公网

```text
Internet
   ↓ HTTPS
Caddy / Nginx
   ↓
RPGmap Server
```

正式公网前必须完成 HTTPS、认证、Session、Origin / WebSocket Origin、上传限制、路径遍历防护、安全响应头、Rate Limit 与自动备份。

## 五、版本与发布策略

应用版本统一使用 `MAJOR.MINOR.PATCH`，例如当前 `1.2.0`。

- 小修复：建议 `1.2.1`。
- 新增较完整功能：建议 `1.3.0`。
- 不兼容架构 / 数据变化：建议 `2.0.0`。

版本提升必须先说明理由并确认，再修改版本号和 `文档/工作日志.md`。

GitHub Release 使用：

```text
v1.2.0
v1.2.1
v1.3.0
```

不再用 `s0-local-server-N`、CI Run Number 或提交次数作为产品版本。

---

## 六、当前推荐开发顺序

1. 完成 1.2.0 Movement / Entity / UI 的人工体验验证与 Bug 修复。
2. 整理多 MapPackage / World 基础。
3. 正式 Server V1。
4. World Store。
5. REST API。
6. WebSocket。
7. GM / Player 权限。
8. Combat / Fog / Dice 等多人玩法。
9. Docker 与公网部署。

不要在 World Store 之前过早引入复杂数据库、完整账号体系或微服务。
