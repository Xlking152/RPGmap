# RPGmap 1.4.1 联机使用说明

本文说明 RPGmap V1.4.1 的 User、Player Identity、Actor Ownership、Combat Turn Lock，以及局域网 / 公网联机流程。

> 当前 V1.4.1 先在 `feat/v1.4.1-player-identity` Draft PR 中验收；正式 `main` 在合并前仍保持稳定版本。

## 1. V1.4.1 的身份模型

V1.4.1 不引入邮箱、注册站点、OAuth 或 JWT。每个 RPGmap World 自己维护一组 Player User：

```text
Connection Session
        ↓
Persistent Player User
        ↓
Default Actor + Actor Ownership
```

- `Session`：本次浏览器 WebSocket 连接，断开后消失。
- `User`：持久身份，Server 重启后仍存在。
- `Default Actor`：该 User 的主要角色。
- `Ownership`：该 User 对各 Actor 的权限。

一个 Player 通常只有一个默认角色，但 GM 可以给同一个 Player 多个 OWNER / OBSERVER Actor。

GM 不需要创建持久 User，GM 通过 GM Secret 登录，并隐式拥有全部 Actor 和全部管理权限。

## 2. User 怎么创建

V1.4.1 同时支持两种流程。

### 推荐流程：Player 先申请，GM 再批准

1. Player 打开 RPGmap 公网 / LAN 地址。
2. 选择 `Player`，填写名称和 Join Code。
3. 第一次加入时，Player 进入“等待 GM 批准”状态，不会立即取得 World 操作权限。
4. GM 点击顶栏“联机”，在“待批准 Player”中看到该玩家。
5. GM 设置正式 User 名称与默认角色，然后点击“批准并绑定”。
6. Server 创建持久 User，为默认角色自动授予 OWNER。
7. Player 立即取得 World 和对应 Actor 权限。
8. Player 第一次批准时会得到一个 **Player Key**，应保存好。

这种流程最适合正常开团：玩家不需要提前注册，GM 保留最终准入和角色分配权。

### 预创建流程：GM 先建 User

适合开团前把角色和玩家都准备好：

1. GM 打开“联机 / Users”。
2. 在“预创建 Player User”填写 User 名称和默认角色。
3. 点击“创建 User + Player Key”。
4. RPGmap 显示一次 Player Key。
5. GM 私下把该 Player Key 发给对应玩家。
6. Player 第一次进入时填写 Join Code + Player Key，即可认领预先创建的 User。

Player Key 不应发到公开群或论坛。

## 3. 为什么需要 Player Key

Cloudflare Quick Tunnel 每次重启通常会生成新的：

```text
https://xxxx.trycloudflare.com
```

浏览器 `localStorage` 按网站域名隔离，因此旧域名保存的自动登录 Token 无法自动出现在新域名中。

V1.4.1 因此区分：

- **Browser Auth Token**：同一个网址刷新 / 重连时自动使用，用户一般不需要手动处理。
- **Player Key**：长期恢复密钥。Quick Tunnel 地址变化后，在新网址输入 Player Key 即可恢复原来的 User。

Server 不保存任何明文 Token 或 Player Key，只保存 SHA-256 哈希。

GM 可以在 User 卡片点击“重发 Player Key”。这样会：

1. 生成新的 Player Key；
2. 废弃旧 Player Key；
3. 同时废弃旧浏览器 Auth Token；
4. 已在线的旧身份会被要求重新登录。

因此“重发 Player Key”也可以作为身份泄露后的强制重新签发功能。

## 4. User 数据保存在哪里

World 状态与权限数据物理分离：

```text
data/worlds/default/world.json

data/worlds/default/access.json
```

`world.json` 保存：

- Actor / Token 状态
- Scene
- Combat
- Chat / Game Log
- 其他共享 World 数据

`access.json` 保存：

- `userId`
- User 名称
- 默认 Actor
- Actor Ownership
- Browser Token Hash
- Player Key Hash
- disabled 状态
- 创建 / 更新时间

`access.json` **不参与 World Snapshot**，Player 不能通过 `world.push` 修改自己的 User 或 Ownership。

## 5. Actor Ownership

V1.4.1 采用三档权限：

| 权限 | 含义 |
| --- | --- |
| `NONE` | 没有控制权 |
| `OBSERVER` | 可作为观察 / 查看权限使用，不允许修改 Actor |
| `OWNER` | 可以完整操控该 Actor |

GM 对全部 Actor 隐式为 OWNER。

一个 Player 可以：

```text
默认角色：张三
OWNER：张三、李四
OBSERVER：王五
```

默认角色必须是 OWNER；如果 GM 把默认角色降到 OBSERVER / NONE，默认角色会自动取消，或者 GM 需要重新指定一个 OWNER Actor。

## 6. Player 能做什么

战斗外，Player 对自己的 OWNER Actor 可以正常进行 RPGmap 操作，例如：

- 选择与移动 Token
- 修改角色资源
- 切换 Form
- 修改自己的角色状态
- 正常聊天
- 测距和个人 UI 操作

Player 不能：

- 创建 / 删除 Actor
- 创建 / 删除 / 重新绑定 Token
- 修改不属于自己的 Actor
- 修改 Combatant 列表
- 修改先攻
- 拖动先攻顺序
- 开始 / 结束战斗
- 推进 Round / Turn
- 删除或改写已经存在的 Chat / Game Log 历史

这些限制由 Server 最终强制执行，不只是隐藏 UI 按钮。

## 7. Combat Turn Lock

GM 负责建立 Combat、填写先攻、排序并开始战斗。

进入：

```text
Combat.state = active
```

后，Player 的 Actor 修改进入 Turn Lock。

例如：

```text
1. 山贼甲   ← GM
2. 张三     ← Player A
3. 李四     ← Player A
4. 王五     ← Player B
```

当前 Turn 是张三时：

- Player A 可以操作张三。
- Player A 即使也拥有李四，也暂时不能修改李四。
- Player B 不能修改王五。
- GM 始终可以操作任何角色。
- Chat / 纯 UI 操作不受 Turn Lock 限制。

GM 点击“下一回合”以后，权限跟随当前 Combatant 自动切换。

Player 端 Combat Tracker 仍可查看当前先攻和回合，但先攻输入、拖动排序、加入/移出、开始、下一回合、结束等控件为 GM-only。

## 8. Server 为什么还要再次检查

V1.4.1 有两层检查：

```text
正常玩家操作
   ↓
Client preflight
   ↓
WebSocket world.push
   ↓
Server authoritative validation
   ↓
accept / world.denied
```

客户端预检用于体验：没有权限的操作尽量直接提示并回滚。

Server 校验才是安全边界。即使有人用 DevTools 手动构造 WebSocket 消息，也不能通过修改完整 Snapshot 来获得其他 Actor、Combat 或 User 权限。

## 9. 最简单的远程联机方法（Windows）

GM 双击：

```text
start-rpgmap-internet.bat
```

启动器会自动：

1. 检测 / 安装 `cloudflared`。
2. 创建 Cloudflare Quick Tunnel。
3. 解析 `https://*.trycloudflare.com` Public URL。
4. 生成 6 位 Join Code。
5. 生成 GM Secret。
6. 启动 RPGmap Server。
7. 打开公网 RPGmap 页面。
8. 打开独立 `RPGmap Multiplayer Info` 信息窗口。

首次玩家通常收到：

```text
Public URL + Join Code
```

已有 User 在新的 Quick Tunnel 地址恢复身份时需要：

```text
Public URL + Join Code + 自己的 Player Key
```

GM Secret 永远只供 GM 使用。

## 10. GM 登录

公网模式：

1. 选择 `GM`。
2. 填写名称。
3. Join Code 可留空。
4. 填写 GM Secret。
5. 加入。

GM 打开“联机”后可以管理：

- 在线 Session
- 待批准 Player
- 持久 Player Users
- 默认角色
- NONE / OBSERVER / OWNER
- Player Key 重发
- User 删除

## 11. Player 首次登录

1. 打开 GM 发来的 URL。
2. 选择 `Player`。
3. 填写名称。
4. 填写 Join Code。
5. Player Key 留空。
6. 加入。
7. 等待 GM 批准。
8. GM 批准后保存显示的 Player Key。

批准前 Player 不会取得 World 写权限。

## 12. Player 后续登录

### 同一网址 / 同一 Tunnel 未变化

浏览器会使用保存的 `userId + authToken`，通常不需要重新输入 Player Key。

### Quick Tunnel 已重启、网址变化

1. 打开新 Public URL。
2. 选择 Player。
3. 填写当前 Join Code。
4. 填写自己的 Player Key。
5. 加入后恢复原 User、默认角色和 Ownership。

不需要 GM 再创建一次 User。

## 13. 局域网联机

同一 Wi-Fi / LAN：

1. GM 运行 `start-rpgmap.bat`。
2. 使用启动窗口里的 `Network` 地址，例如：

```text
http://192.168.1.4:30000
```

3. Player 打开该地址。
4. User / Ownership / Combat Lock 与公网模式完全相同。

LAN 地址通常稳定，因此浏览器本地身份更容易长期自动恢复。

## 14. World Snapshot 与并发

V1.4.1 仍以完整 World Snapshot 作为第一阶段同步模型，并继续使用：

```text
revision / baseRevision
```

避免旧客户端直接覆盖新 World。

V1.4.1 在此基础上增加 Server diff 权限校验。后续如果多人并发编辑频率继续增加，可以进一步升级为 operation / patch 级同步。

## 15. 建议的 V1.4.1 实机验收

至少准备 GM + 两个 Player User：

1. Player A 首次加入 → GM 批准 → 分配角色 A。
2. Player B 首次加入 → GM 批准 → 分配角色 B。
3. A 可以移动 A，不能移动 B。
4. B 可以移动 B，不能移动 A。
5. GM 给 A 再增加一个 OWNER Actor，确认 A 可以控制两个角色。
6. GM 将某 Actor 设为 OBSERVER，确认 Player 不能修改。
7. 开始 Combat，当前 Turn=A 时只有 A 的当前角色可修改。
8. GM 下一回合到 B，权限随 Turn 切换。
9. Player 尝试改先攻 / 排序 / 下一回合，确认被禁用或拒绝。
10. 重启 Quick Tunnel，用新的 URL + Player Key 恢复原 User。
11. 重启 Server，确认 `world.json` 和 `access.json` 都能恢复。
12. GM 重发某 Player Key，确认旧身份失效、新 Key 可登录。

以上通过后，再把 Draft PR 合并到 `main` 并发布正式 V1.4.1。
